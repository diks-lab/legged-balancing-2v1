# 転倒停止中の測定と復帰

作業前8de0a1b、codex/2208-web-ps4。AGENTS.mdとupstream-origin.mdを確認。
PID、CONFIG=0x03、保存FOC校正・PP結果、右−1/左＋1、停止閾値は変更しない。

## 確認した事実と未確定事項

SimpleFOC 2.4.0のBLDCDriver3PWM::disableはPWMとENを遮断し、
BLDCMotor::disableもmotor_statusや校正値は無効化しない。
FOCMotor::loopFOCはenabled判定より前にセンサーを更新する。
従って「ドライバーを無効化しただけでFOC校正が失敗する」とは判断しない。
実機の全×表示が実際にどの最初の異常から発生したかは、ログ未共有のため未確定。

一方、従来コードでは以下が連動していた。
- 車輪異常をIMUのimu_reasonにも適用し、正常なIMUまで無効表示した。
- FOC正常確認がtest_system_readyにも依存し、車輪異常による全体停止をFOCまで×表示した。
- 全体停止後のIMU更新もwheelSensorsOKで止め、通信が可能でも測定停止になった。

この連動を除き、通常転倒停止をセンサー・FOC異常と区別する。

## 測定・復帰経路

通常の転倒停止は従来どおり先に両輪出力を遮断し、目標電圧を0にする。
成功したIMU校正・車輪初期化・FOC/保存校正状態は消去しない。
転倒停止中（emergency_stop_active）はloopFOCを実行せず、専用updateStoppedMeasurementsでEN=LOWのまま
正常な車輪センサーを各1回更新し、MPU6050を1回更新する。
既存の計算値・相補フィルター・速度取得処理を使って制御状態を更新し、
同じ周期の通常取得を重複実行しない。新しい診断専用センサー読取りはない。
停止中のFOC処理時間は0、IMU処理時間は既存の計測領域を使う。

目標0°±2°（両端を含む）に入った最初の周期で、従来の開始経路による
制御状態リセット・目標0°・その時点の車輪位置原点取得を行う。
開始受理後にドライバーを再有効化する。モーター自体が無効なら標準motor.enableを使う。
enableは再アライメントや追加I2C読取りをせず、電圧0から既存の制御へ移る。
保持時間・準備時間・角速度/車輪速度の静止待ちは追加しない。

FOCの表示・正常確認は、初期化完了・保存校正・モーターstatus=ready等で判定し、
ENやmotor.enabled、他部品の異常によるtest_system_ready低下とは分離する。
**復帰の許可にはtest_system_readyも引き続き必要**。表示の分離で停止を迂回しない。

## 実際の異常

- 車輪I2CのNACK/短い読取り等は即時遮断。初期化済みの場合は次の通常周期で再試行し、
  最初の異常履歴を保持したまま、正常な両輪・IMU・FOCを確認して元の意図へ戻る。
  [現在の再試行仕様](wheel-read-diagnostics.md)を参照。
- 全体停止後も、初期化済みIMUは車輪の状態と切り離して更新する。
  共有バスの実際の故障でIMUも読めなければ、その失敗も記録する。
  既存I2Cタイムアウト5 msと停止分岐のyield/delayを維持する。
- IMUの実際のI2C失敗・非有限値・古い測定、FOC非ready等では復帰しない。
  読取りが後に成功しただけでは解除された復帰意図を立て直さない。
- FOCの実際の非ready状態は左右別に記録する。単なるEN=LOWとは区別する。
- 明示停止や異常からの自動再始動は禁止のまま。

WebのIMU表示はIMU自身の取得・校正・鮮度、車輪は両輪センサー、FOCはFOC初期化の
正常性を表示する。例：右車輪NACKだけなら、車輪×・IMU○・FOC○となり得る。
制御は遮断され、first=RIGHT_SENSOR、右理由=I2C_ADDRESS/NACKを表示する。
最初の異常と過去の転倒停止履歴を混同しない。通信停止時の最終情報表示も維持。

## 検証と更新

実ソース関数・実CheckedWheelSensorを使うホスト試験で、停止中100周期の更新を確認。
各周期で両輪各1回・IMU1回、EN=LOW、校正成功状態・保存校正の全バイト保持を確認。
論理的に無効なモーターでも測定し、1.9°へ入った同時刻に復帰・再有効化・位置原点取得。
±2°両端・範囲通過・再転倒、明示停止・古い/無効IMU・FOC異常を回帰。
左右NACKとIMU読取り失敗を注入し、遮断・初回理由保持・復帰禁止を確認。
車輪異常時のIMUとFOC独立表示、20ホストスイート、診断ON/OFFとASan/UBSan、
実Chromium＋模擬JSONの転倒/復帰/実異常表示と既存画面を確認。
ESP32ビルドとLittleFS生成成功。実機での転倒復帰成功は未検証。

静的RAM81,548 Bで増減なし。Flash1,912,821→1,913,033 B（+212 B）。
固定バッファ・スタック・FIFO・機体側履歴・NVS形式を変更しない。

**ファームとLittleFSを両方更新**（data/diagnosis.jsのFOC理由表示も更新）。
全消去やFOC再校正は不要。マージ・実機書込みはエージェントでは行わない。

```sh
pio run -e esp32dev
pio run -e esp32dev -t buildfs
# 利用者が保持方法と対象ポートを確認して実行
pio run -e esp32dev -t upload --upload-port PORT
pio run -e esp32dev -t uploadfs --upload-port PORT
```

機体を保持し、IMU校正中は静止。通常起立開始・転倒後は±2°への進入で即時駆動する。
PS4×等の既存の明示停止を使える状態で、転倒復帰待ち中の姿勢更新と3つの正常表示、
範囲進入での復帰を確認する。異常が出たら配線を動かして故障を作らず、
最初の異常名・左右別理由・IMU tx/rx・FOC詳細を保存する。
実機の通信異常の原因・Wi-Fi/PS4併用・振動・自立成功は別途確認が必要。
