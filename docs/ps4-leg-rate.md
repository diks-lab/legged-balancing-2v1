# 脚上下の最大指令変化速度12ポイント／秒

基準 `d6b9770`。利用者が旧速度4で左スティック下による両脚短縮を実機確認した。
今回、`leg::HeightRate`だけを4→12へ変更する。12での機械側追従・支持／倒立中の挙動は実機未検証。

- 上＝LY正で伸長、下＝LY負で短縮、中央で現在の指令位置を保持。
- DZ±16、再操作の左XY中央±10、符号別端点+127／−128への連続比例特性は維持。
- 最大12ポイント／秒。LY=+72では12×56/111≒6.054、LY=−72では−6ポイント／秒。
- ポイントはサーボ可動量に対する%。実長・機体高さの速度とは限らない。
- UARTの公称50 ms、ServoSpeed=150、加速度15は変更しない。
  12は機体側の位置目標更新速度で、サーボ内部速度150とは別。
- 初回プリロードは取得tickと完全一致し、範囲外の初回保持も変更しない。
  同期・再操作の既存ゲートを維持し、速度変更で初回値を丸めたりHOMEへ移動させたりしない。
- 通常範囲、10 tick余裕、初回受付、左右差・矛盾・片側端での両側停止は維持。
  範囲外は左中央→新しい内向き操作。左右補正は未確認のため無効。
- 車輪制御・右スティック・十字キー予約・接続／停止／異常後の再操作条件は変更しない。

現在の保存4点での通常範囲は、右2.882～29.971%（1940～2034 tick）、
左3.086～29.938%（2094～2181 tick）。値は有効なNVS設定から生成する。
NVS校正値・保存形式は変更せず、再登録は不要。

## 表示

Web「脚部操作・状態」の「上下最大速度・通常範囲」に、ファームから受信した最大速度と
左右別の通常%／tickを表示する。ガイドも12へ更新した。
伸長側の範囲外で上入力を拒否／中央待ちしているときは、
**「短縮して通常範囲へ戻す必要あり。左XYを中央へ戻し、新しい下操作。」**と表示する。
最縮側では逆に伸長が必要と表示し、左右矛盾・片側端の拒否理由は置き換えない。
通信停止時は既存どおり最終受信情報として扱う。

既存1 Hzの詳細JSONへ `leg_rate`（ポイント／秒）と `leg_hint` を追加。
hintは0=なし、1=短縮が必要、2=伸長が必要、3=左右矛盾。
同じSnapshotの実際の左右伸長率と設定範囲から作る表示専用情報で、動作許可条件には使わない。
Webは受信した設定範囲を%へ表示換算するだけで、指令値や制御入力を変更しない。
20 Hzサンプル・通信期限・送信バッファは変えない。

USBには起動時と同期完了時に、最大12と左右の通常範囲を表示する。
拒否時には既存の理由コードと別行の `LEG RETURN: 短縮して通常範囲へ戻す必要あり` を出す。
既存の固定長記録・HTTPタスクでの整形・最大48 B/処理を維持し、受信処理で出力・待機しない。

## 検証

- 実際のPS4コールバック→FIFO→目標更新→UARTを、1／2／5／10／20／50 ms周期で検証。
  最大正負12、比例入力12×56/111、中央保持が同じ実経過時間で一致した。
- 出力した位置フレームごとに、物理受付範囲／通常範囲を検査。
  初回完全一致保持、範囲外の伸長拒否と中央後の短縮、通常範囲への復帰、
  片側端での両側停止・保持を確認した。
- 100%位置から新しい下入力を3秒保持すると、計算・最終送信とも右1822／左2291 tick
  （約64%）、ON1回。位置送信は当該ホスト試行で62回（初回保持・最終送信を含む）。
  機械の実際の位置を読んだ結果ではない。
- 通常への状態遷移とUART送信は同じ瞬間とは限らないため、終端の50 ms送信枠の後まで確認する。
- 既存の範囲・方向矛盾・再接続・異常・NVS・車輪・プロトコル回帰を維持する。
- Webの最大速度・通常範囲・拒否理由、指定2画面サイズと125%相当の可読性を確認する。

## 更新・実機手順

**ファーム＋LittleFSの両方を更新する。保存校正の再登録は不要。**
実機書込み・マージは本作業で行わない。

1. 外部電源コードを脚・車輪から離し、機体を支持して×停止する。
2. 全解放・中央→Share→解放。必要な初回同期後に左XYを中央へ戻す。
3. Web／シリアルの最大12と通常範囲を確認し、**小さな下入力から短縮**する。
4. `calc_RL`・`last_RL`・送信回数を比較し、中央で指令保持することを確認。
5. `NORMAL_RANGE`へ入ってから上操作で伸長を小さく試す。
   片側端で両側が止まることを確認するまで大きな操作を続けない。
6. 指令に機械の追従が不足する場合は、別途その実機結果から判断する。
   今回はServoSpeed・加速度・通信周期を上げて対処しない。

```sh
pio run -e esp32dev
pio run -e esp32dev -t buildfs
# 利用者が支持・停止を準備して実施するコマンド：
pio run -e esp32dev -t upload
pio run -e esp32dev -t uploadfs
```

左車輪不動とコントローラー切断の原因究明は対象外。12への変更で解決したとは扱わない。

## 最終結果・資源

ホスト回帰23組、脚／送信／保存校正／実制御経路／配信のASan・UBSanが成功。
Chromium＋模擬データで最大12・左右通常範囲・短縮の必要理由を確認し、
1366×768／1920×1080の100%および125%相当で重なりがないことを確認した。
ESP32ビルドとLittleFS生成も成功した。実機での12への追従確認とは別である。

`d6b9770`比：静的RAM84,356→84,356 B（**増減0 B**）、
Flash1,948,037→1,949,329 B（+1,292 B）。
Control532 B、State508 B、Snapshot1124 B、シリアル記録器968 B／イベント72 Bは不変。
新しい状態履歴・バッファ・タスク・スタックは追加しない。
追加の1 Hz詳細JSONは27 B、最大確認例1804→1831 Bで既存2048 B内。
20 Hz選択サンプルは不変。実機のヒープ・制御周期は未測定。
