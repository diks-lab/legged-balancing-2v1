# 姿勢角を中心にした診断画面（PR #13）

取得した `codex/2208-web-ps4` の先頭 `d367acf` とローカルの一致を確認して更新。
PRの基準は `codex/2208-short-drive` / `dfd4d0c` のまま。
制御設定の調整ではなく、表示・配信選択と測定状態の改善。

## 初期表示と取得経路

初期選択は **姿勢角・基準角・機体角速度・左右指令電圧の5項目**。
車輪速度は任意選択。以前の7項目は「制御入力の比較」プリセットとして残し、
位置保持8項目・PS4走行／旋回10項目も維持する。

| 項目 | キー・単位・取得元 |
|---|---|
|機体姿勢角|angle_deg、deg。既存MPU相補フィルター後のgetAngleY→LQR_angle|
|基準角|reference_deg、deg。既存angle_zeropoint。走行用目標傾斜ではない|
|機体角速度|gyro_deg_s、deg/s。既存getGyroY→LQR_gyro。姿勢制御の角速度PIDも同じ値を使う|
|左右指令電圧|right_command_v／left_command_v、V。制限・旋回・停止判定後のmove直前、既存モーター符号のまま|

正常初期化後は既存ループが、倒立開始前／通常停止中もMPU更新とLQR状態更新を行う。
姿勢角・基準角は従来から制御armedと無関係にsnapshotへ入っている。
今回は **測定値gyro_deg_sの未開始時nullマスクだけを外す**。
制御角度誤差や未使用制御項のnullは維持し、計測値と制御が有効かどうかを分ける。
停止中の傾き確認に制御角度誤差を代用しない。

センサー異常で既存ループが停止した場合や、初期化前の値を最新実測とは扱わない。
FOC／異常状態、source_seq／age_ms等を併せて確認する。
異常時に観測のためだけのI2C読み取りは追加しない。
他の32項目の符号・フィルター・PID入力との対応、指令／FOCの取得時点差は
[前段の取得経路](control-graph.md#制御値との対応)を維持する。

## 軸と操作

単一Canvas・共通sample_ms軸・固定色・単位付き凡例を維持。
姿勢角と基準角は同じdeg軸。deg軸をプロット左端に最も近い**主軸**に固定し、
角速度・電圧・車輪速度等は独立した補助軸に置く。
異なる単位の軸の線が交差しても、数値が等しい意味ではないことを常時説明する。

通常スケールは次の最低範囲を含む。範囲外は余白を付けて拡張し、値を切り捨てない。

| 単位 | 最低範囲 |
|---|---|
|deg|−20～＋20|
|deg/s|−100～＋100|
|V|−1～＋1|
|rad/s|−6～＋6|

基本操作の「自動スケール（微小変動）」をONにすると、保持中の有効データ範囲で軸を決める。
OFFに戻すと最低範囲へ戻る。他単位の従来の自動範囲は維持する。
軸の上下値表示の桁整形以外に、測定値の丸め・ゼロ化・デッドバンド・新フィルターはない。
**これらは表示範囲であり、転倒閾値や電圧上限を変更するものではない。**

凡例はブラウザー内だけで即時切替。配信変更を送らない。
表示一時停止は横軸の終端時刻を固定し、受信・履歴・異常表示は続く。
一時停止中の凡例／軸切替では、その時刻以前でまだ60秒履歴に残る点だけを再描画する。
古い点が履歴から消えた場合は復元しない。第2の長い履歴コピーは作らない。

## チェック／プリセットの自動反映

`subscribe.js` のSubscriptionControlが、DOMの最新選択と現在の要求を管理する。
WebSocketを再接続して反映する方式ではない。

1. 配信中の変更は最後の変更から **200 ms** まとめて送る。プリセットも同じ規則。
2. 同時に受理待ちにする要求は1件。待機中の変更は最新DOMへ集約し、要求を無制限にキューしない。
3. request_idと選択revisionを照合。古いrequestのACKや、送信後に選択が変わったACKでは
   配信グラフを上書きしない。古い要求完了後、最新選択を送る。
4. 「変更待ち」「応答待ち」「受理：世代／50 ms／項目数」「失敗」を表示。
   受理項目と要求項目の一致も確認する。
5. 全解除は不正なfields=[]のsubscribeを送らず、既存stop JSONを送って測定配信を停止。
   受理後は凡例を空にし、履歴は残す。状態メタデータは既存の1 Hzで継続。
   再チェック／プリセット選択だけでは再開せず、明示的な「配信開始」が必要。
6. 配信停止中の選択変更は送信しない。「配信開始」で最新選択を送る。
   明示停止の状態は手動再接続後も維持する。配信中の切断からの手動再接続は最新選択で再開。
7. UIの受理待ちは2.5秒で有限終了。拒否・内容不一致・送信例外・期限超過では
   自動反映／自動再試行を止める。既に受理済みの機体側配信が続く可能性はあるため、
   失敗表示を走行停止／配信停止の完了とは扱わない。必要時は「配信停止」か再接続で確認する。
   **UIの応答待ちは、ESP32の送信期限を延ばす設定ではない。**

古いACKはrequest_idで除外する。既存のerror応答にはrequest_idがないため、
通常は1件だけの受理待ちへ対応付け、失敗後に自動再試行しない。
タイムアウト後の遅延した失敗を、確定した停止や新しい受理成功として扱わない。

## 維持条件

- 選択された測定項目だけをJSON送信。1クライアント・20 Hz。
- ブラウザー履歴60秒／最大1200点、欠落・無効値・世代／再接続で線を切る。
- 最新snapshot216 B、追加I2Cなし、制御ループ内の動的確保・JSON整形・通信待ちなし。
- PID・検証済み符号・FOC・配線・センサー処理・既存フィルター・PS4ペアリング／操作／停止条件は不変。
- HTTP／WSの既存送信期限・回数・容量、要求解析WDT対策、全スタック、PS4 FIFO/Batchは不変。
- Web切断は走行停止条件にしない。走行指令／PID設定をWebへ追加しない。
- CSVは詳細の補助機能。機体側へ長い診断履歴を戻さない。

## 検証と実機との差

- 停止状態のsampleで姿勢角12.5→−8.25、基準角−0.8、角速度−3.2→1.6を受信・描画。
  実機を手で傾けた試験ではない。

  微小車輪速度0.0001 rad/sを含むプリセット。
- 200 ms集約、受理待ち中の追加変更、古いACK、受理後の凡例更新、再接続回数が増えないこと。
- 全項目解除→stop、停止中のチェック／プリセット変更で送信しないこと、明示再開。
- 凡例即時切替、欠落・無効値、表示一時停止中の履歴／異常更新、切断・再接続、再起動時の履歴分離。
- 1366×768／1920×1080で、初期5項目・全4プリセット・全32項目を選択し、
  折りたたみを閉じた状態のグラフ／凡例／基本操作／補足がviewport内（縦横スクロールなし）。
  グラフ枠：1366幅は姿勢1332×418／走行1332×386、1920幅は各1886×730。

## 更新・実機確認手順

**ファームとLittleFSの両方が必要**。ファームは停止中の角速度配信と新JSルート、
LittleFSは初期選択・軸・自動反映を更新する。古いタブを閉じて再読み込みする。

```sh
pio run -e esp32dev
pio run -e esp32dev -t buildfs
# 利用者が機体を安全に停止・保持して対象ポートを確認後に実行。
# エージェントは書き込みを実行していない。
pio run -e esp32dev -t upload --upload-port PORT
pio run -e esp32dev -t uploadfs --upload-port PORT
```

1. PS4未接続・倒立未開始・1タブで7ファイル完送、受理5項目／50 ms、seq進行を確認。
2. 正常初期化後、モーターを動かす操作をせず機体を保持してゆっくり傾け、姿勢角／角速度が変化し、
   基準角が一定であることを確認。通常の角度軸±20・角速度±100・電圧±1を確認。
   表示範囲外を試す目的で機体の転倒閾値や電圧制限を超えない。
3. 車輪速度を追加し、微小変動で±6より狭くならないこと、自動スケールでだけ拡大できることを確認。
4. 連続チェック変更→受理、全解除→停止、停止中のプリセット変更→未再開、明示再開を確認。
5. 既存PS4手順で段階的に静止倒立・走行等を確認し、角度／基準角・角速度・指令電圧の関係を見る。
   実RAM、制御周期、通信欠落・切断理由も比較する。

マージ・実機書き込みは行っていない。
