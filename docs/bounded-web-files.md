# Webファイルと小さい応答の上限付き送信

## 対象と確認した原因

利用者はf8b67deで http://<IP>/ を開き、最初の処理1件でerrno11が約10秒反復。
アクセス直後にfree7140/largest2292、約105秒後に13972/6900へ回復した。
WebなしのPS4再接続は成功している。最初のURL / は現行ルートで /index.html に対応する。
リポジトリのindex.html=1243 B、style.css=440 B、app.js=1090 B。
実機LittleFSは別書き込みなので、ELF一致だけでそのサイズを確定しない。

Arduino ESP32 3.0.3のstreamFileはStringヘッダー送信後にNetworkClient.write(Stream&)を呼び、
追加1360 Bを確保する。ヘッダーの失敗を上位へ返さず、本文側も短いwriteの未送信分を保持せず
次の読み出しへ進む。NetworkClient.writeは1秒select・10回再試行で、進捗時に回数が戻る。
状態API用の上限はこの経路に適用されていなかった。今回の修正はこの抜けを除去する。
EAGAIN自体の直接理由や、105秒後に戻った領域の内訳まで確定したものではない。

## 送信方式

- HTML/CSS/JSをstreamFileではなく、File.readの固定256 B領域から送る。
- 固定192 Bヘッダー、Content-Length、元のContent-Type、no-store、Connection:closeを使用。
  大きなString、ファイル全体コピー、1360 Bのstream用mallocを使わない。
- 1ファイル上限8192 B。現在の3ファイルは収まる。超過時はファイルを閉じ小さい503を返す。
  将来JSが拡大した場合は、この上限と試験を見直す。無断で上限を拡張しない。
- BoundedHttpWriterの一つのインスタンスがヘッダーと全本文を担当する。
  全体50 msを呼出前に検査、send最大64回、再試行可能エラーは累積3回（再試行最大2回）。
  部分成功や次の読み出しで予算を戻さない。非ブロッキングsend、1回最大512 Bを維持する。
- 同じ読み出し領域と未送信位置を保持し、完全に送ってから次を読む。
  ヘッダー失敗時は本文を読まない。読み出し0/失敗や期限切れでは中断する。
- RAIIでファイル/接続を終了し、404/503の分岐でも開いたファイルを閉じる。
  送信開始後に別エラー応答を重ねない。送信失敗で次の読出し/応答を継続しない。
- 404/503、CSV取得拒否、操作受付の409/202等も同じ小容量・上限付き送信へ統一する。
  操作の受付判定、キューへの投入、制御側の実行処理は変更しない。

50 msはアプリが検査する期限で、File.readやOS send/close内部・スケジューリングまで含む
厳密な実時間保証ではない。socket close後のTCP管理情報や未送達データの回収は別の時系列で評価する。
成功もソケットへの受理を意味し、相手の受信/保存完了を保証しない。

## 初回要求の簡潔な観測

既存の固定32件MEMリングを共用し、要求ごとのSerial行は増やさない。
最初のハンドラーでevent14、Webファイルを開いた時event15、上限付き応答終了時event16を記録する。

| event | cid | arg |
|---:|---|---|
| 14 | ルートID | 0 |
| 15 | ルートID | 実際のfile.size()。未マウント/未取得では0 |
| 16 | ルートID | 下位8bit=結果、上位=HTTPコード（code<<8） |

ルートID: 1=/、2=/style.css、3=/app.js、4=/api/status、5/6/7=velocity/loop/lqr CSV、
8/9/10/11=mode/speed-source/start/stop、12=NotFound。
1の対応ファイルは/index.html。任意URLやクエリー本文を新しく保存/表示しない。

結果: 0=完了、1=入力/整形不正、2=ヘッダー送信失敗、3=ファイル読出し失敗、
4=本文送信/期限/回数上限失敗、5=サイズ超過（低層ヘルパーの拒否結果）。
通常のアプリ側サイズ超過はevent15のサイズと503応答で判定する。
CSV成功応答は旧経路のためevent16を記録しない。初回ログもリング満杯時はlostの対象となる。

## 対応済み・未対応の一覧

| 経路 | 今回の状態 |
|---|---|
| /、/style.css、/app.js の正常配信 | 固定長・共通予算のファイル送信に変更 |
| ファイル欠落/ディレクトリー404、LittleFS未準備503、サイズ超過503 | 固定長・上限付き小応答 |
| /api/status 200/503 | 共通writerで既存の上限を維持 |
| NotFound 404 | 固定長・上限付き小応答 |
| enqueueHttpCommandの202/409（操作4経路） | 応答のみ上限付きへ変更。受付/実行条件は保持 |
| sendTraceBusyResponseの409/503 | 上限付き小応答。元ログ/CSVコピー寿命は保持 |
| beginCsvResponseの正常CSVヘッダー | **未対応**：sendHeader/setContentLength/send(200,text/csv)を使用 |
| velocity/loop/lqr CSVの正常本文・終端 | **未対応**：sendContent(行)とchunk終端、core writeを使用 |
| core内のHTTP要求解析・自動エラー・TCP送受信管理 | **未対応**：アプリから全面置換していない |

CSV成功時には一時コピー10776 Bとcore側送信領域が引き続き必要。
今回の修正でCSVまで低メモリー/全体送信期限が保証されたとは扱わない。
ブラウザーを閉じたPS4試験→Web初期表示→状態更新の比較を優先し、CSV併用は別試験とする。
トレースや既存のCSV機能を削除せず、今後の送信改善またはブラウザー記録への移行と分ける。

## 検証とRAM

tests/http_file_host/run.pyは実際の3ファイルでMIME/Content-Length/本文一致を確認。
確保失敗、部分送信、短い読み出し、ヘッダー/本文/読出し失敗、切断、累積期限/回数、
サイズ上限、空ファイルで両方のcloseを検証する。次のread前に前の全バイトが送られたことをassertする。
ASan/UBSanも成功。既存の固定HTTP応答・HTTP起動・PS4/CSV・解放観測の回帰も成功。

ESP32ビルド成功。RAM **106236 B（前版比0 B）**、Flash **1897157 B**。
data28852 B/bss77384 Bとも不変。初回要求用シンボルはルート2 Bとフラグ1 Bで、
配置差に収まり静的RAM総量は変わらない。32件の記録領域は拡張しない。
読出し256 BとwriterはHTTPの既存スタック上で使い、スタック予約を変更しない。
新しい動的領域やタスクはない。coreのHTTP解析/TCP動的確保までなくなるわけではない。

実機での初回表示成功、errno11反復の解消、TCP回収時期、PS4再接続、内部最大連続領域と
HTTPスタック最小空き量は未確認。dataは変更していない。実機書き込み/マージは行っていない。
