# 脚可動範囲の4点校正

基準 `ee3ee36`。車輪FOCとは別の、サーボ可動量の換算設定。
今回の利用者確定値は右255回／左254回の正常取得、終了reason=NONEから確認された物理端である。

| 点 | 右 ID1 | 左 ID2 |
|---|---:|---:|
| 最縮0% | 2044 | 2084 |
| 最伸100% | 1697 | 2408 |
| 方向・可動量 | 減少で伸長・347 tick | 増加で伸長・324 tick |
| 初回受付（両端を含む） | 1697～2044 | 2084～2408 |
| 10 tick余裕の内側 | 1707～2034 | 2094～2398 |
| 通常駆動（上記∩0～30%） | 1940～2034 | 2094～2181 |
| 明示HOME／10%試験目標 | 2034／2009 | 2094／2116 |

これは**明示保存した場合**の値。ファームの更新だけでは採用しない。
保存値がない初回は「要校正」と今回の4点候補を表示し、脚駆動を禁止する。
旧測定値を自動採用せず、車輪初期化・倒立・診断読取りは無効にしない。
%はサーボ可動量の割合で、実長・機体高さへの比例を保証しない。
各端10 tickは暫定余裕で、荷重・たわみ・ストッパーに対する十分性は実機未検証。

## 今回の確定値を登録する最短手順

1. **外部電源のまま機体を支持**し、電源コードを車輪・脚から離す。
   通常の車輪起立／転倒復帰は有効なので、PS4の×で全停止。脚OFF送信完了を確認する。
2. Web下部の独立した「脚可動範囲の校正」を開き、支持・停止・OFF確認へチェック。
   「校正開始」→「今回の確定4点を候補へ読込」。Shareは不要。
3. 新旧4点、方向・可動量・通常範囲を確認し、「4点を明示保存」。
   **HTTP要求受理とNVS保存成功は別**。機体側の「保存完了・停止／再同期待ち」、
   NVS正常、採用世代と有効値2044／1697／2084／2408を確認する。
4. 保存だけでは脚移動・トルクON・倒立開始をしない。停止は維持される。
   両スティック中央・全解放→Share→解放→新しい左上下操作で再同期。
   初回は取得tickと完全一致でプリロードする。通常範囲外なら、さらに左XY中央→新しい内向き操作。
   最縮側では伸長、最伸側では短縮だけを許可。左右の必要方向が矛盾すれば移動しない。
   片側が進行方向の端へ達したら両側を止める。自動整列・HOME・30%への丸め移動はしない。
5. 電源再投入後、`LEG CALIBRATION BOOT: source=NVS result=OK`と世代を確認する。
   **保存された脚設定があっても、起動時に脚を自動でHOMEへ動かさない。**

USBだけでも、115200 bps、行末を改行にして次を順番に送れる。

```text
:leg begin
:leg candidate
:leg save
```

USBの既存 `d` も全停止。PS4 ×が基本の支持試験操作である。
保存処理タスク未準備なら保存を拒否し、`SAVE_WORKER_UNAVAILABLE`を表示する。
USBを接続しなくてもWebとPS4で運用できる。

## 手作業で4点を再測定する

支持・車輪停止・脚トルクOFF後、「校正開始」。手で無理なく各姿勢へ合わせ、
右最縮・右最伸・左最縮・左最伸の各ボタンを押す。現在位置56/57を1回、非同期で読む。
測定中の最小・最大の自動採用はしない。0として補完せず、失敗点を未取得にする。
候補読込時刻とUARTの実読取り時刻は区別する。
成功した取得値と時刻、失敗の左右・プロトコル詳細を保持する。

```text
:leg begin
:leg r0
:leg r100
:leg l0
:leg l100
:leg save
```

各行の結果を待ってから次の姿勢へ合わせる。`:leg abort`で編集中／読取り中を中断。
Webの「校正中断」も同じ処理。中断・失敗で旧有効値を変えない。
保存のコミット中だけ中断を拒否する。成功／失敗確定までの短い原子的処理として扱い、
中断できたように表示して保存を続ける動作はしない。

校正中はShare・PS4開始／走行・USB駆動要求を拒否する。
車輪の校正要求も拒否し、脚の同期・通常操作・他の読取りとUARTを同時使用しない。
×／USB全停止は残す。校正終了・中断後は中央復帰と新しい操作が必要。
サーボ内部モード・角度制限は書き換えず、自動端探索・位置指令・トルクONは送らない。

## 保存形式と整合性

`Preferences`名前空間は **`leg_range`**、キーは `slot0` / `slot1`。
車輪の `wheel-foc` とは独立している。各レコード32 B、版1、ESP32のリトルエンディアン。

| オフセット | 内容 |
|---:|---|
| 0 | magic `0x4c454731`、uint32 |
| 4 | 世代uint32 |
| 8 | 版uint16、レコード長uint16 |
| 12 | 右0%／100%・左0%／100%、各int16 |
| 20 | 右・左の可動量、各uint16 |
| 24 | 右ID=1、左ID=2、端余裕=10、通常上限=30、各uint8 |
| 28 | 先頭28 BのCRC32 IEEE（多項式`0xedb88320`） |

4点取得済み、0～4095、右減少・左増加、同値禁止、可動量一致、
余裕と0～30%を交差した通常範囲が空でないことを検証する。
版・対象ID・余裕／通常上限・サイズ・CRCの不一致は採用しない。
これらはデータ整合性検査であり、未知の機械的安全性を推測する検査ではない。

最新正常スロットとは別のスロットへ、4点一組のblobを書き、同じ内容を読戻し検証する。
既存の最新正常スロットは消去・上書きしない。書込み途中の電源断で不完全な新スロットは無視し、
旧正常値を選ぶ。完全にコミットされた新レコードが残った場合は次回起動で新世代を採用する。
世代は32 bitの周回を比較し、同世代／半周差ならslot0を優先する。
両方不良なら脚だけ要校正。片スロット不良なら他方の正常値を採用する。
既存レコードの読取り自体に失敗した場合、保護すべきスロットを推測せず保存を拒否する。

起動時だけ主タスクで読む。運転中の明示保存は既存HTTPタスクでNVSを処理し、
固定長の要求・結果ハンドオフを使う。読戻し成功後に主制御タスクが左右一組を採用する。
失敗では実行中の有効設定を変えない。フラッシュ処理は機体停止・校正中だけに限定する。
NVSはLittleFSとは別領域。通常upload／uploadfsで保持されるが、全フラッシュ消去は保存校正も消す。

## 通信・表示・ログ

有効設定から換算、初回受付、余裕内側、通常駆動、手動HOME／10%等、診断値を生成する。
初回受付のコンパイル時 `LEG_ACCEPT_*` 固定設定は廃止。
単独bus_diagnosticも保存済み設定を読み、有効設定がなければ脚駆動を拒否する。
通常ファームの車輪制御・PS4割当・既存通信周期／期限は変更しない。

Webの `leg_calibration` フレームは1 Hzで有効値／候補／各取得時刻／結果／世代／出所を配信する。
既存車輪・脚詳細フレームも1 Hzを維持し、500 msごとに交互に用意する。
20 Hz選択サンプル・固定2048 B送信領域・1クライアントは不変。
通信停止時は「最終受信時の情報」として扱い、現在状態だと断定しない。
各WebファイルはLF／CRLFとも8192 B以内、外部CDNなし、既存の直列取得を維持する。

シリアルの連続軸・通常操作情報は2つの最新値領域へ集約し、合計最大2 Hz。
入力そのものの精度・通知・制御周期は変えない。拒否理由は中央復帰まで重複を抑制する。
同期・受信失敗・範囲・校正・保存等の重要イベントは別の8件FIFOを優先して出す。
重要イベント同士で超過した場合は欠落数を明示する。
最大48 B／処理、USB送信空き以下、受信処理・コールバック内で出力しない。
正常時の生受信ダンプは加えず、既存の失敗時上限付きダンプだけを維持する。

## 検証結果・資源

- ホスト回帰22組成功。校正・脚・実際の車輪／PS4経路・配信のASan/UBSanも成功。
- 今回4点で全113,100組の左右受付tickについて、初回保持が取得値と完全一致することを確認。
  物理端・通常端・1 tick外側・途中・左右差・戻し矛盾と、通信失敗でONしないことを試験した。
  従来の測定値を使う既存回帰fixtureも残し、挙動が変わらないことを別に確認した。
- 実際の停止・PS4入力・4点UART応答・HTTPコマンドキュー・NVSワーカー・主制御側反映を通し、
  校正中の駆動要求拒否、候補だけでは有効値不変、中断・保存失敗で旧値維持、
  保存成功／起動復元だけでは位置・ONが出ないこと、倒しっぱなし拒否を確認した。
- 不足・逆順・同値・不正tick・応答不正／未応答／部分TX、NVS未保存・CRC不良・片スロット不良・
  書込み中断・書込み失敗・読戻し不一致・世代周回を模擬した。実フラッシュの電源断試験は未実施。
- 高頻度の軸変化9,999件でも重要受信失敗／校正イベントを失わず、最新値だけ集約することを確認。
  USB空きなしでも待たず、1回最大48 Bの上限を確認した。
- 実Chromium＋模擬WebSocketで1366×768／1920×1080、100%倍率の既存表示と、
  校正開始確認、4点操作、新旧分離、保存失敗・保存後・通信停止、同値更新のDOM再生成なしを確認。
  主制御の保存結果から生成したJSONも同じ表示経路へ通した。実機のUART／電源断／保存後の伸縮成功とは別。
- ESP32通常ファーム、単独bus_diagnostic、LittleFSイメージ生成成功。マージ・実機書込みはしていない。

実機制御周期・最低空きRAMは未測定。ビルドの静的RAM差を実機の空きヒープ差とは扱わない。
