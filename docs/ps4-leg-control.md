# PS4の高さ・左右傾斜操作

基準93eb444。車輪PID・FULL・DLPF=0x03・保存FOC・右−1／左＋1・起立／転倒復帰・車輪通信再試行は変更しない。
脚・サーボ配置を作り直した後の定数は実機適合済みではない。AngleXの符号も利用者回答「不明」であり、以下の確認が必要。
ジャンプ、自動起立・着地、高さ連動の車輪PID変更は導入していない。

## 参照元の確認

対象はNavbot-EN01の3139f2fb32b38d10611feb905e16f8aa012f2f2e。
[leg_loop](https://github.com/fuwei007/Navbot-EN01/blob/3139f2fb32b38d10611feb905e16f8aa012f2f2e/Src/wl_pro_robot/wl_pro_robot.ino#L470)は、
AngleX+rp.offset_rollをlpf_roll(Tf=0.3 s)→pid_roll_angle(P=8、出力上限450)へ通し、
共通高さ項±8.4×(wrobot.height−32)と合成する。
両サーボ位置から同符号で補正を引くが、取付方向が逆のため脚長の効果は逆になる。
wrobot.rollはこの関数で使われていない。
さらに[robot.cpp::parseBasic](https://github.com/fuwei007/Navbot-EN01/blob/3139f2fb32b38d10611feb905e16f8aa012f2f2e/Src/wl_pro_robot/robot.cpp#L605)は
JSON heightをwrobot.height、rollをrp.offset_rollへ格納する。BLE受信もこの経路へ変換される。
したがって受信rollはoffset経由で作用し得るが、wrobot.rollという変数の使用とは異なる。

移植先は「目標傾斜−実測傾斜」の誤差を明示し、サーボ位置ではなく伸長率で合成する。
上記の数値・位置上限・方向・rollオフセット経路はコピーしない。
新しい脚用ソフトLPFは入れず、既存の相補フィルター後AngleXと脚指令の速度制限を使う。
参照元の車輪PIDの高さ依存変更も持ち込まない。

## 外部電源・段階試験の設定

バッテリー改造は不要。外部電源のまま実施でき、電源種別の判定・電源待ち条件は追加しない。
既定の`LEG_ROLL_DIRECTION_CONFIRMED=0`では上下のみ有効で、AngleXによる左右差補正は一切行わない。
実位置同期時の左右差を保持して共通高さを増減する（各脚0～30%の端では範囲を優先して差を制限）。
左右キーだけでは実位置同期・トルクONを開始せず「方向未確認」として拒否する。
上下と左右を同時に押した場合は上下だけを受理し、左右操作拒否の理由を表示する。
既存IMUのAngleXは表示を続けるが、仮の符号を確定済みとは表示しない。

符号と機構の確認後だけ、`platformio.ini`の既存`build_flags`に以下を追加してファームを再ビルドする。
この設定は車輪方向やセンサー処理を変更せず、脚の左右補正のみを有効化する。

```ini
build_flags =
  -DLEG_ROLL_DIRECTION_CONFIRMED=1
  -DLEG_IMU_ROLL_SIGN=1
```

AngleXが左傾斜で増えるならsign=1、減るならsign=-1。さらに「右脚伸長で左傾斜」の作用と
ID・サーボ変換を実機確認してからconfirmed=1にする。作用が想定と逆なら未確認のまま停止し、
機構と変換を見直す。推測で符号を決定しない。初期配布ファームはconfirmed=0。

## 操作と状態

| 入力 | 動作 |
| --- | --- |
| 十字↑／↓ | 高さ指令を毎秒4ポイント増／減。離すとその高さを保持 |
| 十字←／→ | 方向確認設定が有効な場合のみ、左を正とする傾斜目標を毎秒2°増／減、最大±3° |
| 左右を離す | 傾斜目標を毎秒2°で0°へ戻す |
| 上下／左右の対向同時押し | その軸の目標を保持。左右両押しでは0°への復帰も止める |
| × | 従来どおり車輪全停止＋脚トルクOFF指令 |
| 左スティック／右スティック | 従来の前後進／旋回。割り当て不変 |

PS4の既存全解放・スティック中立確認を使う。接続時にキーが押されていても脚を起動しない。
同じ入力を保持して通知が来なくても、制御タスクの実経過msで操作を進める。パケット数／ループ数で速度は変わらない。
制御更新が200 msを超えて止まった場合は追いつき動作をせず、キー解放・再操作を求める。
FIFOあふれ時も脚入力を中立化し、既存の再解放確認を使う。

静止倒立中に操作でき、脚処理は車輪の制御状態・目標・ゲインを変更しない。
支持した停止状態でも、×全停止→全解放→既存Share/u（車輪ゼロ指令有効化）で脚だけ試験できる。
Share/uは既存の車輪ドライバーを0 Vで有効化するが、倒立を開始しない。脚処理から倒立開始経路は呼ばない。
支持試験ではOptions/tを押さず、Webの「支持した停止試験（倒立OFF）」を確認する。
×を押したままでは全停止が優先され脚は操作不可。×を解放してからShareを押し、Shareも解放して十字操作する。
この場合は起動自動開始が既に解除され、車輪倒立は開始していないことが前提。
走行・減速・走行復帰・開始準備中は脚の新しい操作／補正を停止し、送信済み位置と保持トルクを保つ。
停止後は十字キー解放・再操作で実位置を取り直す。走行と脚操作の同時使用は初期実装では非対応。

PS4切断は高さ増減を止める。既に脚制御中で静止倒立が継続している場合、傾斜目標はゆっくり0°へ戻す。
HOMEへ動かさない。走行からの切断で既存の減速処理が始まる場合は、脚は上記の走行中保持へ移る。
転倒／明示停止／初期化異常等ではOFF指令を優先する。車輪復帰後も古い目標を再送しない。
脚は十字キー解放・再操作から実位置同期をやり直す。車輪の自動復帰条件は変更していない。
一時的な車輪再試行では脚トルクを落とさず、現在指令を保持して脚の再操作・同期を待つ。

## 座標・設定

設定はinclude/LegControl.hに集約。

| 設定 | 初期値と理由 |
| --- | --- |
| ID | 右1、左2（既存） |
| HOME／100%換算 | 右2061／1892、左2026／2208（既存、再検証が必要） |
| 範囲 | 0～30%、整数指令端は右2010～2061、左2026～2081（従来変換の丸めを維持） |
| ServoSpeed／ServoAcceleration | 150／15（既存、参照元ACC=5は採用しない） |
| HeightRate | 4 pp/s、全0～30%に7.5秒かける保守的な初期値 |
| RollRate／MaxRoll | 2 deg/s／3 deg、急傾斜を避ける初期値 |
| RollGain | 1 pp/degのP補正、機構不明のため小さく開始。積分なし |
| DifferentialRate | 4 pp/s、測定角の急変で左右差を即時変更しない。高さと重なる片脚最大8 pp/s |
| RollDirectionConfirmed／ImuRollSign | 既定false／+1（未確認、駆動へ不使用）。確認後だけ上記build_flagsで有効化 |
| SendIntervalMs | 50 ms、通常送信最大20 Hz。安全OFFの初回は優先 |
| ReplyTimeoutMs／SyncMaxAgeMs | 応答10 ms、同期位置250 ms以内。処理を待たず周期間で判定 |

h=共通高さ、d=左右差（右−左の半分）として、右=h+d、左=h−d。
方向確認設定が有効なときだけ、左右差はP×(適用目標−ImuRollSign×既存AngleX)。右を伸ばすと左へ傾くという機構仮定も実機確認する。
hの上下限までの小さい距離を左右差の余裕とし、目標角と補正量をそこへ制限する。
要求角と適用角を分け、hを勝手に変更して可動余裕を作らない。
その後、従来どおり右は位置減少、左は位置増加へ変換する。角度・位置の線形近似は機構校正値ではない。

## 初回同期とUART

起動時は位置・HOME・トルクONを送らない。
初回の明示操作で左右の現在位置レジスター56/57を非同期読取りし、ID・長さ・状態・チェックサム・範囲を確認。
成功した実位置を先に目標レジスターへ書き、その後トルクON。正常位置の平均と差で内部指令を初期化する。
範囲外・未応答等なら動作拒否し、HOMEへ補正しない。同期後に読み続ける方式ではないため、Webの位置・伸長量は「最終送信指令」と表示する。
手で位置が動いた場合や転倒後も再同期が必要。同期期間中に外力で動く機構の出力過渡は実機未検証。

Serial2は従来の1 Mbps・RX16/TX17。新規UARTバッファ・タスク・I2Cアクセスはない。
STSのトルク40、ACC41、目標位置42、現在位置56は既存ドライバーと
[FTServoヘッダー](https://github.com/ftservo/FTServo_Arduino/blob/main/src/SMS_STS.h)を照合。
本機体のSTS3032互換応答は実機未検証。
1回の処理はRX最大16バイト、TX最大1フレーム（最大24バイト）。TX全体の空きを確認してから1回書く。
応答待ち・flush・delay・同一周期内の再試行ループはない。応答欠落時は明示操作をやり直すまで再要求しない。
初回OFFは優先し、送信領域不足時も50 msごとの有限処理で再確認する。ブロードキャスト書込みにACKはない。
WebはON/OFF「指令送信済・応答未確認」とし、トルク実測とは表示しない。

シリアルlは非同期の左右位置読取りだけに変更。目標／トルクを書かず、停止中にIDと現在位置を確認できる。
m/n/o/y/w/!/＠/9の既存絶対位置試験は停止時のみ許可し、自動脚制御の同期・指令表示を無効化する。手動試験の目標はシリアルに表示し、Webの指令欄は自動脚制御の最終指令を対象とする。

## 診断・検証・負荷

下部の既存「詳細診断」内に操作一覧、高さ、要求／適用角、実測左右傾斜、左右指令位置・伸長、制限、受理／拒否理由、トルク指令状態を追加。
脚データは固定長最新Stateを制御タスクからSnapshotへコピーし、既存WebSocketの低頻度診断JSONで最大1 Hz送る。
通常20 Hz測定JSONは選択項目だけのまま。既存送信領域・期限・所有権・要求解析WDT対策を維持する。
data/legs.jsを追加し、HTML→CSS→JSの直列取得と各8192 B上限を維持する。

ホストでは異なる周期で同じ操作速度、キー解放・同時押し、上下限、左右差／誤差の符号、
初回実位置→目標プリロード→ONの順序、断片応答、受信欠落・不正・範囲外、送信不足・部分送信、転倒／復帰／再解放、読取り専用を試験。
実制御関数の回帰で脚処理が追加IMU／車輪読取りや待機をせず、車輪倒立状態を変更しないことも確認。
実Chromium＋模擬データで1366×768／1920×1080、通常画面の配置・診断表示・直列取得を確認する。
ビルドと模擬試験は実機の伸縮・傾斜・倒立成功ではない。

通常位置送信の線上時間は24バイト×10 bit/1 Mbps=240 us、最大20 Hzで0.48%のUART帯域。
これはCPU占有時間ではない。実UARTロック／CPU時間／負荷下の制御周期は実機未測定。
Webに脚処理最大usを記録し、既存loop_usは脚処理も含むようにした。control_dt_msとの比較で実機負荷を確認する。
93eb444時点の固定長Control=72 B、ServoBus=32 B（RX 8 Bを含む）、最新State=56 B。Snapshotは616→672 B（+56 B）。
UARTフレームは最大24 Bの局所配列で、WebSocket送信領域・3192 Bのオブジェクトは不変。
静的RAMは81,852→82,004 B（+152 B）、Flashは1,916,193→1,920,105 B（+3,912 B）。
スタック設定は変更せず、当初導入時のSnapshot局所コピーは56 B増える。Webルート1件追加に伴う起動時ヒープ差は実機で確認が必要。

今回の外部電源試験対応では、93eb444の静的RAM82,004→81,996 B（−8 B）、
Flash1,920,105→1,920,461 B（+356 B）。Control=72 B・ServoBus=32 B・State=56 B・
Snapshot=672 Bは不変。状態modeは既存構造体の余白を使い、新規バッファ・履歴・タスクはない。
脚の1 Hz診断にmode・方向確認設定・符号を追加し、57～59 B/秒増える（JSON最大サイズ試験は既存1 KB内）。
20 Hz測定配信・UART周期/フレーム容量・要求解析/送信期限は不変。
実機ヒープ・CPU時間の差は未測定。

## 書込み・実機手順

ファームとLittleFS両方を更新。マージ・実機書込みは本作業では行わない。

```sh
pio run -e esp32dev
pio run -e esp32dev -t buildfs
# 以下は利用者が安全を確保して実施
pio run -e esp32dev -t upload
pio run -e esp32dev -t uploadfs
```

1. **外部電源のまま、支持した状態で上下確認**：電源OFFでコードに余裕を持たせ、脚の可動域・車輪・床との挟み込みを避けて固定する。
   引っ張られて姿勢が変わらない配置とする。車輪を浮かせ機体を支持し、電源ON後に×で全停止する。
   全解放→Share→Share解放。Webで「支持した停止試験（倒立OFF）」「左右姿勢補正：無効」を確認する。
   `l`は任意の読取り専用確認。↑を短く押し、初回実位置確認→その位置のプリロード→ON→共通高さ増加を確認する。
   ↓・解放時の高さ保持も確認する。取得失敗／範囲外では指令しない。HOMEへ自動移動させない。
   初期方向が逆・範囲が不適合なら×停止して定数と機械位置を確認する。左右キーだけで動かないことも確認する。
2. **左右の符号・伸縮方向確認**：補正無効のまま左右AngleXを観測し、手で左へ傾けて増減を記録する。
   上下操作と左右の最終送信位置から、ID1右・ID2左、右位置減少／左位置増加で伸長することを確認する。
   必要な片脚確認は支持・停止下の既存絶対位置試験を使う。m/n（右2044↔2061）、o/y（左2044↔2026）は、
   現在位置がHOME近傍で17／18 tickの小移動と確認できる場合だけ使用する。未確認なら絶対位置を送らない。
   右脚伸長が左傾斜になることも確認する。確認結果に応じ上記のsignとconfirmedを設定してファームのみ再更新する。
   再び支持試験モードへ入り、手動高さを中間へ上げ、←／→を短く押す。解放時の水平目標0°戻り、
   対向キー同時押し、端での可動制限を確認する。逆補正や異常振動なら×で停止する。
3. **静止倒立中の脚操作**：支持・停止手段を準備して従来の再開始経路で倒立を開始する。
   小さい上下→小さい左右の順で確認し、loop_us/control_dt_ms/脚処理最大us、車輪指令を比較する。
   未確認設定のままなら倒立中も上下のみ。切断・再接続、転倒OFF、復帰後の解放・再同期を確認する。
   走行との併用は対象外。外部電源コードが脚・車輪へ近づかないことを各段階で確認する。

脚再製作後のID・方向・可動範囲・AngleX軸、実際のトルク状態、負荷下の過渡、自立・振動改善は未検証。

## 脚部状態欄の表示整理（557912d以降）

この変更はLittleFS上のHTML/CSS/JS表示だけ。ファーム・制御条件・PS4割当・通信周期・
位置同期・可動範囲は変更しない。更新対象はLittleFSのみ（`pio run -e esp32dev -t buildfs`、
利用者が更新する場合は`pio run -e esp32dev -t uploadfs`）。ファームは557912dのまま使用できる。
更新後はブラウザーを再読込みする。実機書込みは本作業では行わない。

「脚部操作・状態」の固定欄に試験モード、操作可否、左右補正、現在の操作、阻害理由、位置同期、
左右の最終送信伸長率、AngleXと傾斜目標を表示する。行高さを固定し、表示要素は初回のみ作成、
以後は変更されたセルだけ更新する。操作説明と位置指令・回数・処理時間・時刻は別々の折りたたみで既定は閉じる。

伸長／短縮表示は既存1 Hz診断の共通高さ指令の変化から判断する。PS4キーの実測状態や脚の実移動ではない。
同じ診断パケットを再表示しても「伸長→待機」と切り替えず、次の診断で判断する。
内部の操作待ち／受理の違いだけでは表示を交互に切り替えない。失敗・停止・拒否には表示待ちを追加しない。

直近の位置確認失敗・送信失敗・拒否は、ブラウザーで固定長の最新1件だけを別欄へ保持する。
通常待機へ戻れば現在の阻害理由は解除し、直近の失敗は「過去の記録」と表示する。
これはこの画面で受信した範囲の記録であり、画面再読込み／機体再起動で初期化する。
機体側の異常履歴は変更しない。切断・診断鮮度切れでは「通信停止・最終受信時の情報」と明示する。

ブラウザー受信処理で、既にファームが送っているleg_mode・leg_roll_confirmed・leg_roll_signを
保持するよう修正した。通信項目や通信量の追加はない。ESP32のRAM増減は0 B。
Chromium＋模擬データで1366×768／1920×1080、待機・伸長・位置確認・同期失敗・明示停止・
通信切断の固定配置、失敗の保持、同一表示時のDOM更新0件を検証済み。
関連ホスト回帰・直列読込み・LF/CRLFの8192 B上限・LittleFS生成も成功。実機確認は別途必要。

## Share後の古い停止理由の修正（b956b91基準）

実際のPS4経路で「×→全解放→Share→Share解放」を再現すると、Shareは既存の
emergency_stop_activeを解除し、脚のeligibleも成立していた。一方、Control::tickは
ReleaseRequiredだけをIdleへ更新し、ExplicitStop等の外部条件の理由を残していた。
そのため同じState内に「支持試験モード」と古い「明示停止理由」が混在し、Webが操作不可と表示した。
この理由は脚駆動の禁止ラッチではない。位置同期は上下キー操作まで始まらない既存仕様。

修正は、現在のeligible・走行・IMUのガードをすべて通過した後、非動作中の古い外部条件理由だけを
解放確認に応じIdle／ReleaseRequiredへ更新するもの。位置・UARTの実失敗は通常待機で消さない。
Share処理・車輪制御・同期手順・出力条件は変更せず、Shareから目標位置やトルクONを送る処理も追加しない。
Webでは未同期を「実位置確認前」と表示する。試験モードと理由は制御タスクで完成した同じStateを
既存Snapshotへコピーして配信する。通信は1 Hzの脚診断のまま。

回帰は途中のControl初期化や手動seedを行わず、実processPs4Inputと全停止／Share処理を使用。

## 非同期位置応答の判別と失敗記録（bf07bf2以降）

### 仕様と調査結果

既存Servo_STS3032.cppのwriteBuf／Ping／checkHead、およびFTServo公開実装
[64922cda46e56b21b8c1d9e830d936a1941645aeのSCS::Read](https://github.com/ftservo/FTServo_Arduino/blob/64922cda46e56b21b8c1d9e830d936a1941645ae/src/SCS.cpp)と
[SMS_STSのレジスター表](https://github.com/ftservo/FTServo_Arduino/blob/64922cda46e56b21b8c1d9e830d936a1941645ae/src/SMS_STS.h)を照合した。
比較用の公開実装であり、新しいライブラリー依存は追加していない。

- 右ID1・左ID2、位置レジスター56/57から2 B読取。READ命令は2。
- 要求は `FF FF ID 04 02 38 02 CHECKSUM`。右のチェックサムはBE、左はBD。
- 正常応答は `FF FF ID 04 STATUS POSITION_L POSITION_H CHECKSUM` の8 B。
- LENGTHはデータ長+2、パケット全長はLENGTH+4。正常位置応答はLENGTH=4。
- チェックサムはIDから最後のパラメーターまでの加算の下位8ビットを反転する。
- 公開SMS_STSのEnd=0と照合し、位置は下位→上位の順。サーボ方向・位置変換は変更しない。
- 公開ReadはSTATUSを取り出す。本機体は従来どおりSTATUS=0以外を駆動許可に使用しない。

以前の非同期処理は8 Bへ分割データを保持していたが、送信エコーの区別がなかった。
要求の完全なエコーを受信すると命令0x02をSTATUSとして扱い、不正応答になる経路をホストで確認した。
連続FFによるヘッダー境界の重なりも扱えていなかった。**実機の今回の不正応答がエコーだったとは未確定**。
実受信値が従来ログにないため、今回の記録でID／長さ／状態／チェックサム等を切り分ける。

### 受信処理と厳格な駆動拒否

1回最大RX16 B、全体期限10 ms、送信間隔50 msを維持。バイトやエコーが来ても期限は延長しない。
分割フレームを制御周期間で保持し、ヘッダーを上限付きで探索する。先行データの破棄は最大10 B。
正常フレームはID一致・LENGTH=4・STATUS=0・チェックサム一致がすべて必要。

送信したREAD要求、または最後に実際に送信したブロードキャストと**全バイト完全一致**した場合だけ、
エコー候補として分離する。エコーだけでは位置取得成功とせず、別の正常応答が必要。
完全一致前の断片や、似ているが一致しないフレームをエコーとして捨てない。
エコーと同一ビット列の異常応答を通信だけで区別することはできないが、その列だけで駆動することはない。

候補24 B／送信照合24 Bの容量は、既存の最大送信フレーム（両脚SyncWrite 24 B）に合わせた固定値。
UART自体のバッファ容量は変更しない。LENGTH=2の短いエラー応答等もこの上限内で最後まで調べるが、
LENGTHが4と異なれば、チェックサムが正しくても拒否する。容量外／不可能な長さは即時拒否する。
不完全な候補は期限で終了し、次の要求へ結合しない。読取り失敗では位置プリロード・ONへ進まない。
応答待ち・delay・同一周期内の再試行ループ・追加タスクは追加しない。

### Webと固定長記録

最新の受信失敗1件を機体RAMへ保存し、停止・再試行・その後の成功でも消さない。電源断では消える。
現在の同期状態とは別の履歴であり、正常復帰後に過去の失敗だけで「現在も異常」と表示しない。
「位置応答の失敗詳細」で以下を表示する。

- 左右、要求ID、レジスター、要求データ長。
- ヘッダー・ID・長さ・状態・チェックサム・タイムアウトの不一致（複数を同時記録）。
- 各期待値と取得値。未受信／未算出は0で補わない。
- 応答候補サイズ、総観測受信数、要求からの経過ms、失敗時刻。
- 完全一致エコー数、境界前の破棄数、生データ先頭32 B、失敗候補の先頭8 B。
- 生データ記録打切りの有無。総受信数にはエコーと先行データを含む。

短いエラー応答のチェックサム位置は実際のLENGTHから求める。未完成候補のSTATUSは「候補未確定」と表示する。
現在の不正応答理由にも左右・不一致項目を出す。記録は既存1 Hzの脚診断へ含め、Serialの毎バイト出力は行わない。
通信停止時は最終受信情報と表示する。Web機能はleg-reply.jsへ分割し、既存の直列取得とLF/CRLFとも8192 B上限を維持。

leg_rx JSONは次の固定項目順（失敗なしはnull）：
`[失敗ms,経過ms,要求ID,56,2,観測受信数,不一致bit,候補サイズ,期待checksum,エコー数,破棄数,打切り,生データhex,候補先頭hex,受信checksum,checksum算出済]`。
不一致bitはヘッダー1、ID2、長さ4、状態8、チェックサム16、タイムアウト32。
