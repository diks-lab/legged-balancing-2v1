# MPU6050内部DLPFの比較

強い振動は未解決。ビルド・ホスト試験・模擬WebSocketの成功は、実機の
振動改善・自立成功を意味しない。変更前の先頭はdd7bcc9。
AGENTS.mdとupstream-origin.mdに従い、Navbot-EN01の3139f2f版と比較した。

## 変更を分離

1. 診断コミットはCONFIG=0x00を維持。書込み／読戻し検証、短区間集計、Web比較を追加。
2. 設定コミットはinclude/Mpu6050Config.hのDlpfConfigだけを0x03へ変更。

双方ともSMPLRT_DIV=0、GYRO_CONFIG=0x08（±500 deg/s）、ACCEL_CONFIG=0（±2g）。
Navbot同梱版と現行固定版217f66bはこの設定と相補係数0.98/0.02が同じ。
加速度角の式は参照版と現行で異なるが今回変更しない。

[公式Register Map](https://invensense.tdk.com/wp-content/uploads/2015/02/MPU-6000-Register-Map1.pdf)
Register 25/26による比較:

| CONFIG | ジャイロ帯域/遅延 | 加速度帯域/遅延 | 内部出力（DIV=0） |
| --- | --- | --- | --- |
| 0 | 256 Hz / 0.98 ms | 260 Hz / 0 ms | ジャイロ8 kHz・加速度1 kHz |
| 3 | 42 Hz / 4.8 ms | 44 Hz / 4.9 ms | 1 kHz |

CONFIG=3は両センサーに作用する。ジャイロ遅延は約3.82 ms増えるため、
高周波抑制と引き換えに制御安定性が悪化する可能性もある。
内部出力周期はESP32の制御・読取り周期とは別。
現行はFOC→14バイトIMU読取り→制御を毎ループ実行し、固定10 msではない。
実周期はcontrol_dt_msと集計内の実測取得間隔を確認する。

## 適用確認と失敗

モーター無効・mpu6050.begin後・IMUオフセット校正前にCONFIGを書き、
I2C ACK、受信長、read結果、CONFIG/DIV/GYRO/ACCELの読戻しを検証する。
失敗時はIMU_CONFIG_FAILED、両輪遮断、IMU校正・FOC・自動開始へ進まない。
起動Serialに要求値・読戻し値・成否を1回出す。運転中の設定切替はない。
ライブラリの計算式や観測パッチは変更しない。

## 比較表示と集計

項目選択の「振動比較」は角速度・姿勢項・角速度項を選択する。
常設の姿勢角・基準角・左右指令電圧と合わせて確認する。
姿勢は相補フィルター後、角速度は内部DLPF後・65.5で換算・オフセット減算後の
getGyroYそのもの。ソフトLPFはない。rawGyroYも内部DLPF後であり、
内部DLPF前の値は取得できない。「前後」はCONFIG=0/3の別試行で比較する。
表示平滑化・ゼロ丸めによる制御値の変更はない。
姿勢項・角速度項は実際のPID出力、左右指令は制限・旋回・安全判定後の既存値。
停止中に未使用の制御項を有効値として補わない。

詳細診断欄に角速度の約200 ms窓のRMSと最大絶対値を表示する。
RMS=sqrt(sum(gyro²)/有効サンプル数)。平均（DC）を差し引かず、時間加重しない。
既存測定ごとに固定長の二乗和・最大値・点数・時刻・間隔を更新し、窓末に確定。
窓をまたぐサンプル再使用はなく、最新完了窓1件だけを保持する。
無効取得・非有限値を含む窓、窓内250 ms超の間隔はRMS/最大値を無効にする。
IMUが無効または完了窓が500 ms超古い場合もnull／更新停止とする。
サンプル数と最小／最大取得間隔を併記し、取得頻度の差を見落とさない。

角速度を選択したときだけJSONにgyro_window配列を添える。
順序は[CONFIG読戻し,終了ms,窓us,有効数,無効数,最小間隔us,最大間隔us,RMS,最大絶対値]。
既存32項目・購読形式・1クライアント20 Hz・2048 B JSON上限を維持。
追加メタデータは1フレーム128 B以内（20 Hzで最大2.56 kB/sの本文増加）。
ブラウザーの既存60秒/1200点履歴とCSVにも集計を残す。未接続時の過去窓は残らない。

20 Hz波形のナイキスト周波数は10 Hz。高周波は折り返すか見落とす。
RMS/最大値は制御側が実際に読んだ変動を拾うが、未取得の振動は捉えず、
周波数・機械共振・モーター由来を特定しない。RMS低下だけで自立改善としない。
追加I2C読取り、長期履歴、ソフトLPF、PID変更はない。

## 書込みと比較手順（利用者が実施）

ファームとLittleFSの両方が必要。設定0/3間ではファームだけを切り替え、
同じ診断版LittleFSを使用する。全消去は行わず保存FOC校正を維持する。

```sh
pio run -e esp32dev
pio run -e esp32dev -t buildfs
# 対象と保持方法を確認して利用者が実行。エージェントは書き込まない。
pio run -e esp32dev -t upload --upload-port PORT
pio run -e esp32dev -t uploadfs --upload-port PORT
```

診断コミットを別チェックアウトしてビルドすればCONFIG=0の比較基準を再現できる。
設定コミットでは同じ診断のままCONFIG=3になる。

1. 機体を保持し傾いた状態で電源投入、IMU校正中は静止。起動Serialで
   CONFIG要求/読戻し一致・DIV=0・GYRO=8・ACCEL=0・result=OKを確認。
2. 保存FOC・起立待ち・出力遮断を確認。Webで振動比較を選び、詳細診断を開く。
   各試行のCONFIG・実測取得間隔・点数を確認し、ブラウザーCSVを保存する。
3. **0°±2°へ入ると即時駆動する。転倒後も範囲へ戻すと即時復帰する。**
   機体と周囲を保護し、PS4×等の既存明示停止を使える状態で短時間比較する。
4. 同じ支持条件・机・電源・目標・ゲインでCONFIG=0/3を比較。
   停止時、駆動時の姿勢／角速度／各項／左右指令、RMS/最大値、飽和・転倒を確認。
   悪化時は明示停止し、CONFIG=0基準へ戻す。Webの配信停止は機体停止ではない。

右−1/左＋1、保存校正、起立開始／転倒即時復帰、PID・出力限度・停止閾値・FOC・
既存相補フィルター・PS4操作、通信期限・WDT対策・スタック・FIFOは維持。

## 資源と検証

診断追加前: .dram0.data=29,460 B、.dram0.bss=51,816 B、合計81,276 B。
診断追加後: data=29,572 B、bss=51,816 B、合計81,388 B（+112 B）。
内訳: 集計器72 B（最新窓32 Bを含む）、読戻し結果4 B、共有Snapshotの増分36 B。
Snapshotは380→416 B。通信／制御側の一時コピーも各36 B増えるが、スタック容量は不変。
JSON整形・通信は従来どおり通信タスク側。集計は確保なし・定数領域で、
二乗和と最大値は毎取得、平方根は窓確定時（約5 Hz）だけ実行する。
Flashは1,907,857→1,909,409 B（+1,552 B）。RTC・タスク数・FIFO・送信容量は不変。

時刻は既存I2C読取り後の制御値取得時刻。DATA_RDY同期は導入せず、
センサー内部の同じサンプルを複数回読む可能性がある。新規測定数とは区別する。

ホスト試験: 全初期化トランザクションのACK/受信長/read失敗、4設定の不一致、
200 ms境界・全周期取り込み・正負/ゼロ/RMS/ピーク・無効/非有限/長い間隔・時刻周回、
鮮度と選択時だけのJSON、全項目の2048 B内生成、CSVへの集計保存を確認。
既存の制御・起立待ち/即時復帰・明示停止・FOC保存/観測・PS4・HTTP/WDT/確保失敗を回帰。
実Chromium＋模擬JSON: CONFIG=0/3、RMS/最大値、無効化、振動プリセット、
1366×768/1920×1080・100%の通常画面、直列取得、停止・再接続等を確認。
各WebファイルはLF/CRLFとも8 KiB以内。ESP32とLittleFSのビルド成功。
実機のレジスター適用、IMU校正、制御周期負荷・メモリー余裕、起立/復帰、
振動抑制・静止自立はすべて未検証。
