# 脚診断の可読性・指令送信の切り分け

以下の資源・3秒保持の数値は指令診断導入時（4ポイント/秒）の記録。現行の12ポイント/秒は[脚上下速度](ps4-leg-rate.md)を参照。

基準 `a73fb4c`。校正値・受付／可動範囲・速度・PS4割当・車輪制御は変更しない。
左車輪不動と、実機サーボが指令へ追従しない原因の調査は今回の送信観測とは別である。

## Webの重なりの原因と修正

`panels.css`の `.leg-field { height: 4.5em }` と `#leg-freshness { height: 3em }` が原因。
長い拒否理由や通信停止説明が折り返しても、次の行の位置は固定されたまま文字が欄外へ出ていた。
絶対配置はドーナツの中央数値だけで、脚欄の原因ではなかった。

文章行は `min-height` に変更し、短い状態には従来同程度の余白を残し、長文は内容に応じて高さを増やす。
ラベル・値は上揃えにし、長い数値列・生データ・遷移preにも折返しを設定する。
1200 CSS px以下は1列、800 CSS px以下はラベル／値も縦配置。
同じDOMと変更された値だけの更新を維持するが、長文で隣の行が動くことは許容する。

主画面の診断が閉じているときは、従来の画面高さ・グラフ中心配置を維持。
診断／脚校正を開く場合はmainを自然な文書の高さにし、グラフ領域を圧縮して後続へ重ねない。
外側detailsの縦スクロールを残し、内部detailsの多重の高さ制限・スクロールは外す。
スクロールで読めることを優先し、文章を切ったり隠したりして重なりを解消したように見せない。

## シリアルの新しい観測

PS4の受理された左入力の開始／終了／方向変更を、制御側で固定長に記録する。
動いているように見えなくても、要求と適用入力を区別する。
生入力は `raw_LX_LY`、実際に脚目標へ適用した正規化入力は `applied`（上下／左右）。
`START` は入力要求の開始で、実際の回転開始やON応答を意味しない。
同期中・範囲外保持・左右補正未確認等では、入力があっても適用0になり得る。

```text
LEG MOTION: START ms=... raw_LX_LY=0/-128 applied=-1.000/+0.000 calc_RL=1697/2408 valid=1 calc_ms=...
LEG UART: last_RL=1697/2408 valid=1 last_ms=... goal_sent=1 wait=0 failed=0 flags=3B
LEG TORQUE: ON_SENT_UNCONFIRMED on_sent=1 wait=0 failed=0 reason=ACCEPTED blocker=NONE edge_coalesced=0
```

上は書式の例。開始周期の経過時間が0なら `applied=0` で、その後のPROGRESSを見る。
`START` / `CHANGE` / `END` と、最大2 Hzに集約した `PROGRESS` を出す。
中央復帰後、最後の目標がまだUARTへ送られていなければ、後で `FINAL_UART` を記録する。
送信成功だけでなく遮断／失敗で送信処理が終わった場合も同じFINAL_UARTになり得るため、
必ず `goal_sent / wait / failed`、flags、理由と目標差を併せて確認する。

| 表示 | 意味 |
|---|---|
| `calc_RL` / `calc_ms` | 既存の `Control::target()` で計算した右／左tickと計算時刻 |
| `last_RL` / `last_ms` | 位置フレーム全体をUARTへ渡せた右／左tickと時刻。実測位置ではない |
| `valid=0` | 未取得／無効。併記数値を有効な0 tickとして扱わない |
| `goal_sent` | 24 Bの位置フレーム全体のwrite成功回数。READ・ON・OFFを含まない |
| 位置の `wait` | UART送信空き不足で、位置フレームをwriteしなかった回数 |
| 位置の `failed` | writeの実返却長が24 Bに足りなかった回数。送信成功に数えない |
| `on_sent` | 12 BのONフレーム全体のwrite成功回数 |
| ONの `wait / failed` | ONの送信空き不足／返却長不足。OFFは含まない |
| `ON_SENT_UNCONFIRMED` | ONフレームをUARTへ送信済み、サーボの応答／適用は未確認 |
| `OFF_SENT_UNCONFIRMED` | OFFフレームをUARTへ送信済み、物理トルクの応答は未確認 |
| `flags` | 1=計算値有効、2=最終送信指令有効、4=可動制限、8=同期済、16=脚制御active、32=左入力ゲート通過 |
| `blocker` | 同じ確定状態の拒否／待ち理由。`NONE`も実動作確認を意味しない |

回数は起動後のPS4脚制御経路の累積で、32 bit最大値に達したら飽和する。
旧手動試験のドライバー直接送信を合算したカウンターではない。
これらの値は診断だけに使用し、制御条件・送信周期・再試行を変えない。
追加の位置読取りも行わない。

同期・受信失敗・拒否・校正等の重要8件FIFOとは別に、移動境界を2件だけ記録する。
連続軸と移動の出力は同じ500 ms予算を共有し、合計最大2件/秒。記録時刻は変えない。
長押し中の通知回数や微小な倒し量変化ごとにイベントを積まない。
境界が集中した場合は最初と最新側へ集約し、`edge_coalesced`で観測欠落を明示する。
重要FIFOを入力変動で埋めず、重要イベントの出力を先に処理する。

受信処理／コールバック内では出力しない。制御側では固定長コピーとカウンター更新だけ。
既存HTTPタスクの消費側で整形し、1処理最大48 B・Serialの送信空き以下で出す。
空き不足で待機しない。USB未接続でも制御動作は同じ。

## フレームの照合

既存 `src/Servo_STS3032.cpp` の `SMS_STS::SyncWritePosEx`、
`on_all_servo / off_all_servo`、`SCS::syncWrite / Host2SCS` と照合した。

| 内容 | 既存ドライバー／非同期バス共通 |
|---|---|
| 宛先・命令 | broadcast ID254、SYNC_WRITE `0x83` |
| ON／OFF | 開始レジスター40、1 B/サーボ、ID1→ID2、値1／0、全12 B |
| 位置 | 開始レジスター41、7 B/サーボ、全24 B |
| 各位置データ | ACC=15、位置L/H、時間=0 L/H、速度=150 L/H |
| 数値 | リトルエンディアン、負値は既存STSの符号・絶対値形式 |
| チェックサム | IDからデータ末尾までの8 bit和の反転 |

ホストでは既存ドライバー本体をそのままコンパイル・実行し、実際に生成した各バイトと比較する。
ON／OFFと3秒間に生成した位置フレームは一致した。実装を似せた比較用モデルとの比較ではない。
ASanで保持される未定義の基底readSCS用vtableには、テスト専用の到達禁止リンク関数だけを用意する。
既存のSCSerial、フレーム生成、非同期UARTのコードは置き換えない。

SYNC_WRITEは応答を返さない方式であり、書込み返却長だけでサーボ受信・追従は確認できない。
USBシリアルの診断は、UART経路へ渡せたことまでの観測である。

## 実機での切り分け順序

**ファームとLittleFS両方を更新**する。本作業では実機書込み・マージを行わない。
通常の起立開始条件は有効なので、機体を支持し×停止。外部電源コードを脚・車輪から離す。

1. Webの校正有効値とPS4接続を確認し、全解放→Share→Share解放で支持試験へ。
2. 左上下操作の初回同期は、取得tickのプリロード・保持だけ。既存どおり、中央復帰後の新しい操作が必要。
   右1697／左2408 tickなら両方100%。中央→新しい下入力を3秒間保持し、中央へ戻す。
3. START/PROGRESS/END/必要ならFINAL_UARTで、`applied` が短縮側、`calc_RL` が右増加・左減少になったかを見る。
4. `last_RL`も同方向へ変わり、`goal_sent`が増え、`wait / failed`とON送信状態を確認する。
   計算だけ変わる場合は送信待ち／失敗・最後の送信位置との違いを調べる。
   どちらも変わらない場合は同期段階・入力ゲート・可動制限・`blocker`を見る。
5. **全フレームをUARTへ送信できたことを確認してから**、実機のサーボ追従・電源・配線・受信側を調べる。
   未追従の原因を、今回の送信観測だけで特定・解決済みとしない。

```sh
pio run -e esp32dev
pio run -e esp32dev -t buildfs
# 以下は利用者が支持・停止を準備して実行する。
pio run -e esp32dev -t upload
pio run -e esp32dev -t uploadfs
```

## 検証結果と資源

- ホスト回帰23組成功。脚送信・脚制御・保存校正・実制御／PS4経路・配信のASan/UBSan成功。
- 実際のPS4コールバック→FIFO→入力ゲート→目標更新→フレーム生成→UART writeを通した。
  右1697／左2408 tickの完全一致保持→中央復帰→新しい下入力を3秒保持すると、
  計算目標・最終送信値は **右1739／左2369 tick**、位置フレーム **61回（初回保持を含む）**、ON **1回**。
  速度4ポイント/秒の100→約88%に対応する。入力通知の追加がなくても更新・送信が続くことを確認した。
- 既存STSドライバー本体を実行したON／OFF／位置フレームと全バイト一致。
  UART空き不足・部分writeでは送信成功回数が増えず、待ち／失敗を分離する。
  高頻度9,999周期の境界変化でも、重要な受信失敗を移動イベントより先に保持・出力できることを確認した。
- 実Chromium＋模擬データで、長い実際の拒否文・校正値・最大長生データ・遷移4件を使用。
  1366×768／1920×1080の100%、125%相当で、文章内の行・別要素・別行の矩形が重ならず、
  親欄外に文字が出ないこと、横スクロールが不要なことを確認した。
  125%相当は物理サイズを固定しCSS viewportを1/1.25、DPRを1.25にした検証
  （1092×614／1536×864 CSS px）。実機PCのネイティブ拡大操作そのものは未試験。
  通常100%のグラフ・凡例・基本操作は従来どおりスクロール不要、同じDOMの値更新も確認した。
- ESP32ビルド、LittleFS生成成功。実機書込み・マージはしていない。

`a73fb4c`比の静的RAMは **84,132→84,356 B（+224 B）**、
Flashは **1,946,549→1,948,049 B（+1,500 B）**。

| 領域 | 変更前 | 変更後 |
|---|---:|---:|

| Control（State内包） | 496 B | 532 B |
| 最新Snapshot（State内包） | 1088 B | 1124 B |

内包する領域を合算しない。全静的RAM値にはコンパイラーの配置・最適化差も含む。
既存スタック・PS4 FIFO・2048 B TX・制御用フィルター・校正形式・通信期限は不変。
追加のWebサンプル項目・センサー読取り・長期履歴はなく、Web通信量も変更しない。
ホストでは1周期16 RX／1 TX、診断48 B／処理の上限と待ちを追加していないことを確認。
実機の制御周期・最低空きヒープ・物理UART波形・サーボの応答／動作は未測定。

保存校正の再登録は不要。通常ファーム／LittleFS更新で既存NVSは保持される。
**ビルド・ホスト送信成功と、実機サーボの追従成功は別である。**
