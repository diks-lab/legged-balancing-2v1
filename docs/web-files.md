# Web配信とファイルシステム

基準: `codex/2208-short-drive` の `dfd4d0c`。
速度P=0.25、位置P=0.1、FULLの位置項およびFULL/ATTITUDE+SPEEDの速度項の反転は保持する。

## ビルド・書き込み

PlatformIOの `esp32dev` 環境を使用する。Wi-Fi設定は追跡対象外の
`include/ssid.h` に `include/ssid.example.h` を参考に作成する。

```sh
pio run -e esp32dev                   # ファームのビルドのみ
pio run -e esp32dev -t buildfs        # data/からLittleFSイメージを生成（書き込まない）
# 以下は利用者が実機を停止・保持し、対象ポートを確認して実行する
pio run -e esp32dev -t upload --upload-port <PORT>    # 通常のファーム書き込み
pio run -e esp32dev -t uploadfs --upload-port <PORT>  # dataの書き込み
```

通常のuploadだけではdataは更新されない。初回・Web更新時はuploadfsも必要。
`no_ota.csv` の既存領域をLittleFSに使用する。既存の別形式のファイルシステムを
そのまま読むことはできない。uploadfsはファイルシステム領域全体を書き換える。
マウントは `LittleFS.begin(false)` とし、失敗時はフォーマットしない。
Webファイルがない場合は404、マウントできなければ503を返す。
いずれも倒立開始やモーター指令を発生させない。

## Webの役割

`/`、`/style.css`、`/app.js` はdata内の独立ファイル。
`GET /api/status` は250ms間隔で取得した状態のコピーを返す。
UIは1秒ごとに取得し、失敗時は前回値であることを表示する。
停止理由、角度と基準、初期化・センサー・モーター状態、モード、速度取得元、
トレース件数を表示する。既存の3つのCSV URLは保持する。
Webの開始・モード変更・速度取得元変更は診断用の折り畳み欄に残す。
POSTは202で受付を返す。安全ゲートによる実行拒否はシリアルと状態表示で確認する。
STOP TESTも既存のstopBalanceTestを呼ぶ。PS4の明示的な全停止とは区別する。

## 制御周期と記録保持

同期WebServerは専用のCore 0タスクで動作する。
制御ループはソケット送信・ファイル読み出し・接続待機をしない。
状態はFreeRTOSの長さ1のキューで渡し、Web操作もキュー経由で制御ループに渡す。
HTTPタスクからPIDやモーター、センサーを操作しない。
CSV要求時は制御ループが固定長のリングバッファをコピーし、
HTTPタスクがそのコピーを整形・送信する。倒立・開始待ち・極性試験・直接駆動中は拒否する。
コピー取得後に倒立を開始しても、送信対象は独立したコピーなので記録と競合しない。
転倒時の記録保持・停止理由・再開始時のリセット方針は既存実装を保持する。

ソケットの低速送信が制御ループを直接停止させる経路を除去した。
ただしCPU・Wi-Fi割り込み・メモリー帯域の共有は残る。
250msごとの状態整形と停止時の固定長コピーの所要時間、低速クライアント接続中の
最大制御周期は実機での計測が必要であり、ハードリアルタイム保証ではない。
脚操作や既存のシリアル診断出力に伴う待ち時間も実機評価が必要。

今回の環境では実機へのファーム/data書き込みは行わない。

## HTTPタスク起動失敗への対応

`9bae8ef` は実機で `HTTP task unavailable` を報告した。
この表示は動的タスク作成が `pdPASS` を返さなかったことを示す。
当時のヒープ値・戻り値は記録されておらず、総量不足と断片化のどちらかは未確定。

修正版は8,192バイトのスタックを削減せず、TCBと共に静的予約する。
LittleFS/Wi-Fi開始前に静的タスクを生成し、準備完了をatomicで通知するまで待機させる。
CSVは同期WebServerが1件ずつ処理するため、要求された種類だけを独立コピーへ保存する。
3種類のコピー領域はunionで共有する。元の制御用リングバッファと記録保持方針は変更しない。
前のコピー要求がタイムアウトして処理中なら、新しい種類への切替を拒否する。

起動時に `HTTP memory stage=...` として次を記録する：
- 全体の空きヒープ、内部8-bit RAMの空き量と最大連続空き領域
- 予約スタック、TCB、状態キュー要素、CSVコピー領域のバイト数
- キュー作成前、タスク作成直前/直後、LittleFS後、Wi-Fi後の各段階

タスク作成APIの戻り値は `HTTP task create: api=static result=OK/NULL`。
静的APIは整数エラーコードではなくハンドルを返す。続く `HTTP task running` は
タスク本体が実際に実行されたことを示すが、HTTPサーバー開始やWi-Fi成功とは別。
成功確認には従来の `WiFi trace HTTP server started.` とページ/API応答も必要。
キュー/タスク作成失敗時は確保済みキューを解放し、制御ループにWeb処理を移さない。

`/api/status` 末尾の `HTTP resources` は `stack_free_min_bytes`（起動後の最小残量）、
空きヒープ、内部最大連続空き領域を返す。ESP-IDFではここでのスタック単位はバイト。
静止・CSV3種類・ファイル配信後に確認し、残量を根拠に容量を評価する。
静的予約はタスクスタックの動的確保を回避するが、Wi-Fi等のヒープ不足を保証しない。
ビルド/ホスト試験と実機での起動・スタック余裕の確認は区別する。

## 現在の起動順序と診断（PR #13）

mDNSは無効。ESPmDNSを読み込まず、`MDNS.begin()` を呼ばない。
接続先として表示するのは、取得したIPv4アドレスの `http://<IP>/` だけ。

1. 起動直後から両輪ENをLOWにする。シリアルとPS4ライブラリを初期化する。
2. LittleFS、HTTPキュー/静的タスク、Wi-Fi接続・非ゼロIP取得、HTTPのTCP待受を確認する。
   この段階では車輪ドライバー初期化、センサー/I2C、FOCを開始しない。
3. 待機中はループでENをLOWに保ち、PS4入力・シリアル・Webの状態配信を続ける。
   WebはFOC未初期化でも `/api/status` から確認できる。LittleFSがマウントできない場合も
   状態APIは利用できるが、通常ページは503となり、FOCへは進まない。
4. 必須のWeb事前確認がすべて正常な場合に限り、制御ループ側が既存の車輪/IMU/FOC初期化を
   一度だけ実行する。初期化パラメーターとアラインメントタイマーは変更しない。
5. 両輪FOCと初期化後のセンサー確認も成功したら起動を確定し、通常の操作メニューを
   起動ごとに一度だけ表示する。タスク作成成功だけでは表示しない。

PS4は従来どおりFOC開始の必須条件ではない。未接続、あるいはライブラリ初期化失敗でも
Web診断を使える。PS4接続を待つ新しい条件は追加していない。
FOC完了前の操作要求は診断で観測できるが、既存の初期化ゲートにより走行開始を拒否する。
Web STARTは初期化前に409を返し、FOC完了後へ遅延実行しない。
FOC完了時はPS4の最初のパケットの解放・中立確認をやり直すため、待機中に押し続けた
開始ボタン/スティックだけで倒立や走行を始めない。

IP取得時のUSBシリアル表示（115200bps、下記のIPは例）：

```text
WiFi: 接続完了 (connected)
WiFi DHCP IP: 192.168.1.42
HTTP access URL: http://192.168.1.42/
WiFi trace HTTP server started.
（既存の両輪FOC初期化ログ）
STARTUP: state=READY foc=READY littlefs=READY wifi_ip=READY http=LISTENING
（操作メニュー）
```

キュー/タスク/LittleFS/Wi-Fiモード/HTTP待受などの起動失敗は段階と状態を表示し、
FOCと通常メニューを開始しない。接続/IP取得はHTTPタスクで1秒ごとに確認し、
5秒で `WIFI_TIMEOUT` / `IP_TIMEOUT` と接続状態・IP・経過時間を出す。
接続待ちループを制御側に追加しない。起動待機中に復旧した場合は一度だけFOCへ進む。
ハードウェア初期化失敗は従来どおり再起動が必要で、自動的に再アラインメントしない。
初期化前の全停止も解除せず、`FOC_INHIBITED_FULL_STOP` として出力を遮断したままにする。

FOCの段階間でも事前条件を確認する。初期化中にHTTPタスクが事前条件の喪失を検出すると、
原子的な状態で中断を保持し、GPIOのENだけをLOWにする。制御側は次の段階へ進まず、
初期化失敗として終了する。原子的な起動確定との比較交換により、起動確定後のWi-Fi切断を
新しい走行停止条件にしない。通常時のPS4切断・転倒・センサー異常などの停止方針は維持する。

Webには `Web preflight` のLittleFS/Wi-Fi-IP/HTTP状態、起動段階、FOC未初期化/処理中/失敗/完了、
PS4診断を表示する。初期化失敗後もWeb/PS4診断を続ける。再接続やIP変更では数値URLを
再通知するが、FOCとメニューを重複実行しない。手動の `h` / `?` と既存停止手段は残す。

## タスク間の共有データとI2C

- センサー初期化、MPU校正、FOC、PS4指令の受理と実行、状態スナップショット作成は
  同じ制御ループ側で行う。両方のI2CバスをHTTPタスクから操作しない。
- Webの事前確認、接続/IP/HTTP待受、FOC完了・中断・起動確定はatomicで通知する。
  HTTPタスクから車輪PWM、ドライバーAPI、サーボ、PIDを操作しない。
  起動中断時のGPIO遮断だけは、既存のアラインメントタイマーと同じ仕組みを使う。
- `captureHttpStatus` / `publishStartupPhase` は制御側のキャッシュだけを読み、
  I2C取得を行わずに状態をキューへコピーする。HTTP側はそのコピーを配信する。
- LittleFSとキュー/タスク設定はHTTP実行許可のrelease/acquireより前に完了する。
  PS4の生入力・ボタン履歴・操作結果は制御側だけが更新し、HTTPから直接参照しない。
- 新しいUSB診断は通常HTTPタスクがキュー済みのPS4文字列を出力する。
  HTTPタスク生成に失敗した場合のみ、車輪を遮断した待機ループが出力を担当する。
  同じ送信バッファを両タスクで同時に更新しない。

既存の静的8KiBスタック、CSVコピー共用、起動メモリー診断と状態APIのメモリー情報は維持する。
FOCアラインメント・MPU校正は従来の同期処理なので、その間のPS4入力/通常状態更新には
間隔が空く。HTTPは段階ごとの最後のコピー（`sample_ms` 付き）を表示する。
ネットワーク監視もHTTP処理の進行に依存し、起動中の遮断検出やシリアル共有ロックの
最大遅延を保証しない。停止応答、I2C、通信負荷と制御周期は実機での確認が必要。


PS4のBluetoothコールバックは、接続/切断/入力のコピーをportMUX保護の固定長FIFOへ
渡すだけとし、Serial・Web・I2C・モーター・停止APIは呼ばない。
操作状態と診断の更新は制御側、Webはキュー済みの最新コピーを配信する。
同期FOC中も通知は保持するが、有限FIFOのためあふれ時は回数・エッジ集計と
停止要求を別途保持する。[イベント処理と制約](ps4-events.md)を参照。
