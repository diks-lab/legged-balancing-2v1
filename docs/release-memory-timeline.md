# PS4再接続とHTTP解放の時系列観測

f0dd1fd実機で初回接続後internal_free=9692/largest=8180、再接続HID確保時828/660。
途中の所有領域は未確定なので、この版は解放待ち/重複/リークを判断するための観測だけを追加する。
4,112 BのHID要求、PID/FOC/Classic設定/ペアリング/操作/停止条件、FIFO/トレース/スタックを変更しない。
WebSocketも追加しない。

## ログ

`MEM event=N http_active=N ms=N cid=N arg=N free=N largest=N lost=N`

msは同一起動のmillis、free/largestは内部8bit領域。
イベントのargは下表。http_activeはその時点のHTTPハンドラー処理中件数を記録する。
コールバック内ではメモリー数値の取得と短いcritical sectionでの保存だけを行い、
Serial/Web/I2C/モーター操作を行わない。公開接続/切断コールバックは既存FIFO通知を先に渡す。
既存ライブラリのエラー出力は維持し、この観測からの出力は追加しない。

| event | 意味 | cid / arg |
|---:|---|---|
| 1 | PS4初期化前 | 0 / 0 |
| 2 | PS4初期化処理後 | 0 / 既存ライブラリ初期化結果。実接続成功とは別 |
| 3 | 接続要求到着（再接続も同じ） | CID / PSM。17=control、19=interrupt |
| 4 | 両チャネル設定完了、enable前 | CID / 0 |
| 5 | 公開APIの接続通知 | 0 / 0。最初の入力に伴う通知 |
| 6 | 生の切断通知入口 | CID / ack_needed |
| 7 | DisconnectRsp呼出から復帰 | CID / API戻り値。これだけでリンク全解放と扱わない |
| 8 | チャネル解放後の通知 | CID / 0または切断確認結果。アプリのCIDクリア後も記録 |
| 9 | 公開APIの切断通知 | 0 / 0 |
| 10 | HID確保直前 | control CID / identifier。244=enable、17=LED等の出力指令 |
| 11 | DataWrite復帰直後 | control CID / identifier + (result << 16)。所有権はスタック側 |
| 12 | HID確保失敗直後 | control CID / identifier。既存の中断処理へ進む |
| 13 | 切断/確保失敗後の残量 | 0 / 予定経過時間100,500,2000,10000 ms |

IDF 5.1.4の「切断確認」とack不要の切断通知はチャネル解放後の経路を確認済み。
ack必要な通知は解放前のことがあるので、event6だけで解放済みとは判定しない。
event8もACLリンク全体やHCIの全領域回収を保証しない。CIDを消すだけの処理とは区別する。

切断後のサンプルはHTTPタスクが採取する。FOC観測中やHTTP待機で遅れる可能性があり、
実際の経過はmsで判断する。新しい接続要求/接続通知で前回の遅延サンプルを終了する。
即時再接続ではevent3が次の比較点となる。再接続確保失敗では遅延サンプルを再開する。
切断直前の継続的な残量は下記5秒集計の最新値とイベント点を使うため、直前瞬間の値と同一ではない。

## HTTP集計

`MEM HTTP ms=... requests=... active=... send_failed=... after_free=... after_largest=... min_free=... lost=...`

最大5秒に1行。要求ごとのSerial出力は行わない。
requests/activeは登録ルートとNotFoundのハンドラー単位。解析前に失敗した不正要求等は含まない。
RAIIでハンドラー終了時にactiveを戻す。同期処理なのでHTTPタスク自身の集計時には通常0だが、
同時期のBTイベントには処理中のactiveも保存する。

send_failedは検出した送信失敗操作の累計で、失敗要求数ではない。同じ要求のヘッダー/本文で
複数回増え得る。状態APIの上限付き送信結果、coreのvirtual write/write_Pの短い戻り、
WebファイルstreamFileの送信バイト不足を記録する。送信処理・再試行条件自体は変更しない。
coreが直接書く一部のchunk footerやTCP受理後の配送失敗を完全に数えるものではない。

after_free/largestはhandleClient復帰後、要求数が変わった時と最低5秒間隔で取得する。
通常の2msループごとにヒープ走査しない。min_freeはこれら取得点の最小値で、
全実行期間の瞬間的最低値ではない。WebServerの後処理後でもTCPのACK待ち/TIME_WAITは残り得る。

## 上限・共有データ・出力

レコードは20 B×32件。固定リング満杯時は新しいレコードを破棄しlostを増やす。
待機、再確保、無制限履歴はない。欠落があれば全イベントの復元を保証しない。
一つの短いportMUX critical sectionでBT callbackとHTTP側を同期し、
ヒープ取得・文字列整形・Serial出力中にはこのロックを保持しない。

表示はHTTPタスクだけが担当し、FOC観測中は保留。イベント行は最大10行/秒、
1回のSerial.writeは48 B以下かつavailableForWriteの範囲内とし、flush/送信空き待ちはしない。
HTTPタスク内の既存PS4診断と観測行の途中出力が交互にならないよう排他する。
制御側のPS4処理を止める排他ではない。既存の他のSerialログとの割込みまでは防がない。
HTTPタスク作成失敗時はこの観測のSerial排出を行わず、リング上限/lostで扱う。

## 最初の実機比較

1. ブラウザーを閉じ、シリアルログを起動から保存する。初期化/最終起動結果も残す。
2. PS4接続→入力確認→切断。10秒後サンプルまで待ち、再接続→切断を複数回繰り返す。
3. 同一起動内で短い間隔の再接続も行い、旧チャネルのevent8と次のevent3/10の順を比較する。
4. その後Webを1タブ開き、同じ接続/切断間隔で比較する。初期比較ではCSV取得を行わない。
5. 必要ならWebを閉じて数分待った値も確認し、TCP解放待ちと累積低下を分ける。

time、CID、enable/LED種別、http_active、lostを併せて判断する。
同一の静穏条件へ戻るか、初回だけ低下して安定するか、回数に応じて累積低下するかを比較する。
数値取得やSerial排出も観測負荷であり、この版で改善/悪化しても原因を即断しない。
実機の解放完了やリーク有無は、このログを確認するまで未確定である。

## 観測の常駐RAM

ELF/mapでは **105,340 → 106,236 B、896 B増**。
.dram0.dataは28,164→28,852 B、.dram0.bssは77,176→77,384 B。
レコーダー680 B（レコード640 B＋管理40 B）、同期8 B、出力行192 B、
出力位置/時刻等24 B、出力所有フラグ1 Bで追加シンボル合計905 B。
配置差9 B減を含め、最終的な増加は896 Bとなる。新しい動的確保・タスク・スタック予約はない。
観測にも常駐RAMと取得処理の負荷があるため、f0dd1fdの残量と単純差分で原因を決めず、
本版の同一起動・同条件の推移で比較する。free/largestは別APIで近接取得し、
その間の他タスクによる確保/解放を原子的に排除するものではない。

PS4低層の観測フックは既存の1.1.1版/全体SHA照合パッチに追加した。
既知の従来安全修正版からも全体SHAを確認して移行する。未知ソースは拒否する。
観測が不要になった際はフックだけを撤去し、必要なNULL/中断補正を同時に失わないこと。
