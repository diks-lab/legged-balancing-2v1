# 車輪センサーの最初の異常と遮断中の通信確認

基準3133b2a。53587 msの右AS5600受信不足の原因（配線、電源、ノイズ、タイムアウト等）はまだ確定していない。
今回追加するのは原因切分けの観測であり、異常を無視する回避処理ではない。

## 固定長記録

左右それぞれ、最初の失敗と最新の遮断中確認を各1件保持する。リング履歴や動的確保はない。
AS5600のアドレスは0x36、RAW_ANGLE開始レジスターは0x0C、要求は2バイト。
記録内容は、要求開始ms、処理時間us、最後の転倒停止ms、endTransmission(false)の戻り値、
requestFromの実受信数、available数、high/lowのread値、レジスター、要求数、直前の制御フラグ、結果。
−1は未実行／未取得。転倒時刻0は未記録（起動直後ms=0と区別できない）。
制御フラグは1=初期化完了、2=倒立制御、4=遮断、8=片輪極性試験、16=校正、32=起立待ち、64=転倒復帰待ち。
制御周期入口でPS4入力処理後、車輪読取り前に設定し、最初の失敗時にコピーする。
初期化中の読取りでは既定のフラグ0。最初の記録は後続の確認では上書きしない。

使用coreのWire.cppではendTransmission(false)は反復開始を予約し、実際のwrite/readは
requestFrom内のi2cWriteReadNonStopで行う。したがってtx=0だけでバス通信成功とは言えない。
requestFromの戻り値はrxLengthで、内部esp_err_tは公開APIから取得できない。
既存のI2C_SHORT_READ/TIMEOUTという名称を保持するが、今回の観測だけでタイムアウトと断定しない。
受信不足・available不足ではhigh/lowを余分に読まない。追加の正常時I2C読取りはない。
異常時のGPIO遮断を先に行い、記録コピー・Serial出力は後に行う。

## 停止後の確認

車輪異常でtest_system_readyを解除した後、制御タスクだけが1秒に最大1回、
異常をラッチしたセンサーのRAW_ANGLEを確認する。既存のI2Cタイムアウト5 msは変更しない。
確認前に両輪ENをLOWにし、Sensorの角度／速度キャッシュ、ready、fault、校正値を変更しない。
成功しても過去の異常・初期異常理由・停止履歴を消さず、FOC・倒立を再開しない。
通常の転倒停止からの即時復帰仕様も変更しない。

USBには最初の失敗記録を出し、確認結果は正常／失敗種別が変わった時だけ出す。
Web詳細診断には「最初の読取り異常（保持）」と「遮断中の通信確認」を別行で表示する。
確認結果は通信回復／現在も失敗／未確認・確認更新停止を区別する。
2.5秒超の確認データ、Web切断・配信停止時は現在の通信成功／失敗と断定しない。
再起動後はこのRAM記録は残らない。既存RTC確保失敗記録は変更しない。

## 配信と容量

通常sampleの2048 B上限を維持するため、車輪詳細は別のJSON type=wheel_diagnosticsで最大1 Hz送る。
同じ1クライアントWebSocket、固定送信領域、部分送信位置・期限・再試行上限を使い、キューを増やさない。
通常20 Hzサンプルが先に処理され、送信領域が埋まった場合の欠落は既存のseq／droppedで通知する。
診断フレームはsampleのseq・実測時刻・履歴を更新しない。boot_idが一致するものだけ画面へ反映する。
wheel0／wheel1配列は、最初の記録12要素、最新確認12要素、確認回数の計25要素。
各12要素の順序は ms, elapsed_us, fall_ms, tx, received, available, high, low, reg, requested, context, result。
resultは0=未実行、1=成功、2=tx失敗、3=受信不足、4=read値不正、5=角度不正。

WheelReadRecordは28 B、WheelReadDiagnosticsは64 B／輪。センサーの追加コンテキストは8 B／輪。
整合した配信用Snapshotは480→608 B（+128 B）。WebSocketオブジェクトは3192 Bで不変、送信容量も不変。
ESP32静的RAMは81540→81820 B（+280 B）、Flashは1913029→1914957 B（+1928 B）。
スタック設定・FIFO・トレース容量を変更せず、Snapshotの局所コピー分は128 B増える。

## 検証・書込み

ホストではNACK・受信不足・不正値、処理時間／フラグ／転倒時刻、異常保持、成功確認後の再失敗、
1秒間隔、遮断、起立／復帰禁止、全項目＋両輪異常でもsample／別診断が固定枠へ収まることを確認。
実Chromium＋模擬データでは両画面サイズ、異常保持と通信回復の別表示、切断・鮮度・既存画面を確認。
実機の断続異常、実際の停止後I2C回復、メモリー余裕は未検証。

ファームとLittleFS両方の更新が必要。

```sh
pio run -e esp32dev
pio run -e esp32dev -t buildfs
# 利用者が停止・安全を確保して実行
pio run -e esp32dev -t upload
pio run -e esp32dev -t uploadfs
```

本作業ではマージ・実機書込みをしない。
試験は最初に車輪を浮かせて既存停止手段を準備し、異常時のWHEEL READ first行とWeb詳細を保存する。
遮断を維持した状態で確認結果の推移を観察し、回復表示だけで駆動が再開しないことを確認する。
PID、保存校正、FOCパラメーター、DLPF、方向係数、停止閾値は変更しない。
