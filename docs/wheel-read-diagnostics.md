# 車輪読取りの一時遮断・次周期再試行

2262e58の「車輪通信失敗は再起動まで停止」を変更する。
最初の異常履歴は保持するが、初期化済みセンサーの現在の通信失敗は次の通常制御周期で再試行する。
受信0の原因そのもの（電源・配線・ノイズ等）は未確定であり、今回解消したとは扱わない。

## 制御周期と復帰

1. 制御タスクで右、左、IMUを各1回取得する。失敗した車輪のコールバックは直ちに両輪ENをLOWにする。
2. 失敗周期はPWM・指令をゼロにし、loopFOC／move／倒立計算へ進まない。SerialとHTTPの停止要求処理は継続する。
3. 次周期に各センサーを1回ずつ再試行する。同一周期内のリトライループはない。
4. 両輪とIMUの最新値・鮮度、保存校正・FOC正常性を確認して、元の制御意図へ戻る。

倒立中は制御を継続し、転倒復帰待ちは意図とTILT_STOP履歴を保持して、固定0°の±2°へ入った周期で既存経路から復帰する。
保持時間・成功回数待ち・ボタン操作は追加しない。
明示停止・初期化失敗・無効保存校正・IMU／FOC異常は通信成功だけで解除しない。
初期化・FOC校正中は自動再試行の対象外。既存初期化バリアとタイムアウトは維持する。
異常中のu／手動開始も拒否する。PS4の割り当ては変更しない。

正常時もloopFOC前に角度を取得するが、その後のSensor::updateは確認済みキャッシュを使うため、I2C取得回数は増えない。
通信タスクによるI2C読取り、追加タスク、並列バスアクセスはない。
従来の1 Hz確認は初期化等のハード停止時に残し、通常運転の再試行待ちには使わない。

## SimpleFOC 2.4.0のキャッシュ

Sensor::updateは負のgetSensorAngle戻り値を受けると、角度・時刻・full_rotationsを変更せず戻る。
この経路を維持し、失敗値をキャッシュへ書かない。回復の正しい角度は同じ周回判定で取り込む。
回復周期では両輪の速度差分基点・時刻を現在の角度へ合わせ、速度を0で再シードする。
SimpleFOC速度LPFは同じTf／Tsのまま状態だけ再初期化し、既存の制御速度LPF、10 ms診断速度、PS4速度窓、PID状態もリセットする。
これにより古い速度、停止期間をまたぐ微分、旧フィルター出力を再使用しない。
位置原点・モード・走行目標・固定姿勢目標0°は変更しない。復帰後の次の測定から速度計算を再開する。
初回速度0は回復処理の再シード値であり、その瞬間に車輪が物理的に静止したとの測定ではない。

失敗中に絶対エンコーダーが複数回転した回数はAS5600の1周角だけでは復元できない。
既存SimpleFOCの周回追跡の制約は残る。試験で確認したのは単発・連続失敗と周回境界付近での復帰であり、
長い通信断中の高速・多回転や実機出力の安全性を保証するものではない。

## 履歴と現在状態

左右各1件の最初の異常と最新の通信結果を固定長で保持する。履歴配列・動的確保はない。
AS5600アドレス0x36、RAW_ANGLEレジスター0x0C、要求2バイト。
記録は要求開始ms、処理時間us、最後の転倒停止ms、endTransmission(false)戻り値、
実受信数、available、high/low read値、reg、要求数、直前制御フラグ、結果。
−1は未取得、転倒時刻0は未記録（起動ms=0との区別なし）。
フラグは1=初期化完了、2=倒立制御、4=遮断、8=極性試験、16=校正、32=起立待ち、64=転倒復帰待ち。
最初の異常と起動内の最初の原因は上書きせず、制御読取りの失敗回数は飽和カウンターで保持する。
正常受信では現在のfault／errorだけを更新し、初期化・FOC成功状態は消さない。

Web詳細は「最初の異常（保持）」と「現在の読取り正常／失敗・次周期再試行」を別表示する。
現在状態は50 msサンプルのfault bitで確認し、詳細記録は別JSON type=wheel_diagnosticsで最大1 Hz更新する。
26要素配列の先頭12要素は最初、次12要素は最新、最後2要素は確認回数・制御読取り失敗回数。
各12要素の順序はms, elapsed_us, fall_ms, tx, received, available, high, low, reg, requested, context, result。
resultは0=未実行、1=正常、2=tx失敗、3=受信不足、4=read値不正、5=角度不正。
詳細の確認回数にはハード停止中の診断確認も含む。通信停止・古い記録は現在の正常／失敗と断定しない。
Serialは最初の記録と遮断／回復の遷移時だけ出す。遷移ログは最大1 Hzで、短周期の点滅による大量出力を抑制する。

使用WireはendTransmission(false)で反復開始を予約し、requestFrom内で実転送する。
tx=0は受信成功の保証ではない。受信側内部esp_err_tは公開APIで取得できないため、受信不足だけでTIMEOUTと断定しない。
既存RTCメモリー確保失敗記録は変更しない。

## 検証・容量・更新

20組のホスト回帰、実SimpleFOC Sensor／LPF／PIDを使う試験、sanitizer試験、
Chromium＋模擬データで1366×768／1920×1080の表示を確認した。
単発→次周期正常、連続、両輪失敗、正逆周回境界、転倒待ちと±2°進入、
明示停止・u拒否、無効IMU・無効校正、失敗周期のゼロ指令／遮断、回復周期の速度再シードと有限・上限内出力を確認。
実機での通信復帰・出力過渡・自立・走行・振動は未検証。

ESP32ビルド・LittleFS生成を実施。固定送受信領域・期限・WDT対策・スタック・FIFO容量は変更しない。
Snapshotは608→616 B（+8 B）、WheelReadDiagnosticsは64→68 B／輪。WebSocketは3192 Bで不変。
静的RAMは81,820→81,852 B（+32 B）、Flashは1,914,957→1,916,193 B（+1,236 B）。
診断JSONは失敗回数分だけ増え、通常サンプルの項目・20 Hzは不変。
PIDゲイン、FULL、DLPF=0x03、保存FOC、右−1／左＋1、転倒閾値、姿勢の丸め・ドーナツ符号は変更しない。

ファームとLittleFSの両方を更新する。

```sh
pio run -e esp32dev
pio run -e esp32dev -t buildfs
# 利用者が停止・安全を確保して実行
pio run -e esp32dev -t upload
pio run -e esp32dev -t uploadfs
```

本作業ではマージ・実機書込みをしない。
書込み後は、次の正常周期で自動的に駆動が再開し得る仕様であることを確認し、安全に支持した状態で試験する。
最初の異常、失敗回数、現在の通信、左右指令・速度、転倒復帰待ち／倒立中を記録して比較する。
