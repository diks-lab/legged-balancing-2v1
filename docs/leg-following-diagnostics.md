# 脚左右4°/秒と実位置追従診断

取得したブランチ先頭は82c1220。取得時点で、それ以降の変更はなかった。
AGENTS.md、upstream-origin.md、脚操作・校正・送信診断文書を確認して変更した。

## 変更と維持

脚専用のRollRateを2→4°/秒へ変更。比例操作と中央で0°へ戻す処理が同じ定数を使う。
最大±3°、P=1ポイント/度、左右差4ポイント/秒、上下12ポイント/秒は変更しない。
目標変化を速めたことは、実際の脚やAngleXが同じ速さで追従する保証ではない。
左Xの既存変換、左Y正＝伸長、右スティック走行、十字キー予約も不変。
IMU符号−1、脚NVS、通常範囲・10tick余裕、初回完全一致保持、中央／新操作の条件、
範囲外の内向き復帰と左右補正禁止、車輪制御・保存FOCは変更しない。

## 非同期の現在位置確認

既存ServoBusの制御タスク所有UARTとServoReplyパーサーを共有する。
脚の同期・ON済み・active時だけ、左右交互に最大1 READ/500ms（各脚約1Hz）。
停止中の既存読取り専用測定・設定読取り・校正とは別の診断で、追加タスクは作らない。
初回同期の取得位置をこの診断値で書き換えたり、制御へフィードバックしたりしない。

- READはID1/2、位置56/57番、2B。ID・長さ・状態・チェックサム・エコー判別を既存パーサーで検証。
- 応答期限10msは延長せず、毎サービス最大16 RXバイト・1 TXフレームを維持。
- 位置指令の50ms予算と、追加READの500ms予算は分離。
  期限到達した位置指令／OFFを優先し、READ待ちでも指令を待たせない。
  位置送信の間のサービスで8B READを送るため、全UARTフレームが50ms間隔になるわけではない。
- UART空き不足では待機せず、その回を送信待ち失敗と表示。部分writeも読取り送信失敗と表示。
  同周期で再試行せず、次の低頻度機会へ進む。通常時の追加通信はTX16B＋RX16B/秒。
- 読取り失敗は診断専用。新たな停止判定・トルク操作・HOME移動を追加しない。
  既存の初回同期失敗時のON禁止は維持。
- 停止・切断では待ちを中断し、取得値を過去値とする。新しいREADを続けない。
  更新時刻は正常応答を検証した時刻だけ。失敗時に0を正常実位置として登録しない。

## 値の区別

Web下部「脚部詳細」に、同じSnapshotの計算目標と時刻、UART最終送信指令、
取得実位置、READ要求／取得時刻、READ時点の指令とその送信時刻を表示する。
差は **実位置−最新UART指令**（tick）。取得と最新指令は同時刻ではないため、
移動中には通信時間差を含む。指令と一致してもサーボのON・受理状態を確証するものではない。
未取得・読取り中・失敗・中断・古い値・Web通信停止を区別し、
正常応答から1500msを超えた値は現在値として表示しない。最終取得tickは過去値として残す。
取得実位置は機構の高さや荷重下の脚実長そのものではない。

詳細JSON `leg_follow` は次の固定構成。

```text
[計算有効, 計算右tick, 計算左tick, 計算ms,
 [状態, 取得tick, 取得ms, READ要求ms, READ時指令tick, その送信ms, issues],  // 右
 [状態, 取得tick, 取得ms, READ要求ms, READ時指令tick, その送信ms, issues]]  // 左
```

状態：0未取得、1読取り中、2正常応答、3読取り失敗、4停止／切断後、5TX空き不足、6部分write。
issuesは既存ビット：1ヘッダー、2 ID、4長さ、8状態、16チェックサム、32タイムアウト。
正常応答は通信検証の意味であり、可動範囲内／受理／到達の保証ではない。

USBの既存LEG MOTION／UARTが計算と最終送信を表示し、追加LEG FEEDBACKが
左右の取得tick・取得ms・READ時指令／ms・差（実位置−READ時指令）・age・状態を表示する。
Webの差とUSBの差では比較する指令時点が違う。各時刻を見て比較する。
失敗・古い値ではerror=UNKNOWN。失敗時のtick/msは現在値ではなく最終取得情報。
最新値へ集約する専用1記録だけを追加し、連続診断全体の最大2件/秒予算を共有する。
重要8件FIFOを読取り結果で埋めない。整形はHTTPタスク、出力は最大48B/回・空き以下で待機しない。
受信処理・コールバックで出力しない。USB未接続でも制御は同じ。

## edge_coalescedの原因

82c1220ではRecord::Payloadが小さいRxFailure（64B）だけを初期化していた。
MotionState（76B）のcoalescedはオフセット64Bで、その先は初期化対象外だった。
境界キューをpopする経路は実カウンターで上書きするが、最新PROGRESSをpopする経路は
未初期化の値をそのまま出せた。実機の巨大値はこの経路と整合する。

最大メンバーmotionでunionを初期化し、動作記録生成時にもMotionState{}を明示する。
unionの最大サイズが変わった場合はstatic_assertで検出する。
構造体のコピーは型付きの全体代入で、旧サイズによるmemcpyはなかった。
出力はuint32_tをunsigned longへ明示変換して%luへ渡しており、書式不一致はなかった。
値の丸め・任意の上限制限で隠す修正はしていない。

## 試験と資源

- ホスト回帰23組が成功。productionのPS4→FIFO→制御→UARTで4°/秒、比例入力、±3°、
  中央戻しを1/5/10/20/50ms周期で検証。範囲外補正禁止・再操作・位置保持も回帰確認。
- 同じ経路で非追従の模擬サーボ実位置を返し、計算／送信値と別に保持・配信することを確認。
- 読取りの正常・分割・別ID・長さ・状態・チェックサム・タイムアウト・部分TX失敗を検証。
  読取り中でも位置送信し、切断では読取りを中断、OFFを応答期限待ちせず送信することを確認。
- 汚した記憶領域へRecordを構築する試験、上下／左右／読取り記録混在、実coalesced数を検証。
- 脚・UART・NVS・実制御・配信のASan/UBSan成功。
- Chromium＋模擬データで1366×768／1920×1080、100%と125%相当の可読性を検証。
  値の区別・失敗／古い値／切断をホストJSでも確認。実機に接続したブラウザー試験ではない。
- ESP32ビルド・LittleFS生成成功。直列読込み、LF/CRLF双方8192B上限を維持。

82c1220比：静的RAM84,516→84,700 B（+184 B）、Flash1,949,613→1,951,301 B（+1,688 B）。
ホストの内訳はFollowing40B、State508→548B、Control532→572B、Snapshot1124→1164B、
ServoBus144→148B、シリアル記録器1112→1208B。Record84B／出力器304Bは不変。
追加は最新観測と上限付き最新シリアル記録で、長期履歴・タスク・動的送信領域は作らない。
整形時の差文字列はローカル固定16B。タスクスタック設定・UARTバッファ容量は変更しない。
詳細JSON最大試験値1831→1981B、既存2048B内。追加は既存1Hz詳細メッセージだけ、
20Hz選択サンプルは不変。実機のヒープ・制御周期・追従成功は未確認。

## 更新と実機確認

**ファーム＋LittleFS両方を更新。脚・車輪校正の再登録は不要。**
実機書込み・マージは本作業で行わない。

```sh
pio run -e esp32dev
pio run -e esp32dev -t buildfs
# 利用者が支持・停止手段を準備して実施する場合のみ
pio run -e esp32dev -t upload
pio run -e esp32dev -t uploadfs
```

1. 外部電源コードを脚・車輪から離し、機体を支持。×→全中央・解放→Share→解放。
2. 初回同期が取得tickをそのまま保持することを確認。範囲外なら中央後の内向き操作で戻す。
3. 通常範囲の中間で小さな左右操作→中央。要求目標が4°/秒、±3°以内で変わることを見る。
4. 計算tick→UART指令→実位置tick・取得時刻→AngleXの順で比較する。
   UART指令だけ変わり実位置が変わらなければ、そのログを保存して次の切り分けに使う。
   変化した指令と実位置の時刻差、READ失敗、通信停止を混同しない。
5. 上下混在、小さな左右補正、停止・切断を支持状態で確認してから静止倒立中へ進む。
   走行との同時操作は対象外。傾斜・追従の実機成功は未検証。
